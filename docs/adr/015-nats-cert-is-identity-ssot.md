# ADR-015: NATS Cert-Is-Identity — Single Source of Truth

**Status:** Accepted
**Date:** 2026-04-14
**Deciders:** platform team
**Related:** ADR-014 (mTLS-only auth — legacy shared account removed), ADR-011 (Schema Ownership Model), CLAUDE.md architectural hierarchy

## Context

The 2026-04-14 production outage (`Authorization Violation` cascade
across every backend service) exposed a systemic defect in the platform's
NATS authentication architecture: two parallel auth mechanisms were
live simultaneously, and drift between them caused the outage.

**Pre-refactor state:**

1. **mTLS + `verify_and_map: true`** (load-bearing): every per-service
   mTLS client cert has `CN=<service_name>` (e.g. `billing_service`).
   The NATS server (running `nats-tls-enabled.conf`) verifies the cert
   at TLS handshake, then maps the cert's CN directly to the NATS user
   identity in the authorization block. CONNECT-frame `user`/`pass`
   fields are IGNORED by the server.

2. **Username/password auth** (dead weight): nats.conf had
   `{ user: $NATS_AUTH_USER, password: "$NATS_AUTH_PASS" }` entries
   that were `$-interpolated` from env vars. docker-compose passed
   the env vars to the NATS container AND to every backend service
   (which sent them in CONNECT frames that the server promptly
   ignored). Helm `natsAuth.*User` / `.*Pass` values populated the
   same env vars in Kubernetes.

The two mechanisms required the service name to be identical across
**five** configuration layers:
  - `nats.conf` authorization users (parsed from `$NATS_*_USER` env)
  - `infrastructure/docker/scripts/generate-internal-certs.sh` CN list
  - `docker-compose.droplet.yml` `x-nats-*-env` anchor defaults
  - `infrastructure/helm/aquaculture/values.yaml` `natsAuth.*User`
  - `.github/workflows/deploy-digitalocean.yml` provisioning block

When the deploy workflow's `generate_credential` helper was
(incorrectly) used for `NATS_*_USER` values, it produced random
32-char strings that won `.env` interpolation over the
`${NATS_*_USER:-default}` fallbacks. Cert CN was `billing_service`,
nats.conf user became `aXbC7Kd...` — every service boot failed with
`Authorization Violation` and production was down.

The incident hotfix (`d77eddf9`, `set_canonical()`) was Tier-2
Automatic per CLAUDE.md's hierarchy: it heals `.env` at deploy time.
But drift between the five sources remained structurally possible —
any one of them could be edited without the others, and drift wouldn't
be caught until runtime.

## Decision

**Cert CN IS the identity. Nothing else.**

Specifically:

1. **Remove the entire username/password auth layer.** nats.conf user
   entries have no `password:` field. docker-compose, helm, and deploy
   workflow stop provisioning `NATS_*_USER` / `NATS_*_PASS` env vars.
   Client factory and event-bus library omit user/pass from the
   CONNECT frame in mTLS mode. verify_and_map handles identity alone.

2. **Single source of truth at `infrastructure/nats/services.yaml`.**
   One file lists every NATS service with its `name` (matches cert CN)
   and its publish/subscribe ACLs. Downstream artifacts derive from
   this file:
   - `nats.conf` authorization block: generated by
     `scripts/nats/generate-nats-conf.py` (Python + PyYAML; idempotent;
     writes between `# BEGIN GENERATED` / `# END GENERATED` sentinels)
   - Cert CN list: hand-maintained in lockstep with services.yaml by
     `generate-internal-certs.sh`; CI test asserts 1:1 match
     (BACKLOG-NATS-002 will later derive the cert script from
     services.yaml automatically)
   - Helm + docker-compose: no longer reference service usernames at all
     (removed in P7/P6)

3. **CI invariant test (`e2e/tests/integration/nats-invariants.spec.ts`).**
   Asserts services.yaml ↔ nats.conf ↔ cert CN list. Any drift fails
   the build before it reaches production.

4. **Dual-mode client factory for dev compatibility.** The NATS transport
   owns this factory at
   `platform/libs/event-bus/src/nats/nats-connection.factory.ts`; direct
   clients consume the narrow `@platform/event-bus/nats-connection` port.
   TLS-enabled (+ cert) → cert-only mode: CONNECT frame omits user/pass.
   TLS-disabled (local dev, no mTLS) → user/password fallback still works
   against a NATS server with authorization users[] that have passwords.
   Dev doesn't use the generated production nats.conf — dev mounts a
   different config. Keeping the factory below `backend-common` preserves a
   one-way platform dependency graph instead of making the transport adapter
   depend on its application consumers.

## Rationale

### Why remove passwords entirely (not keep as defense-in-depth)

Per CLAUDE.md hierarchy, Make-Impossible > Automatic > Detectable >
Documented. Keeping passwords as defense-in-depth would be Tier-2:
operators would need to rotate them, sync them across five sources,
and remember they're ignored by the server under verify_and_map.

Removing them is Tier-1:
- No password in nats.conf → server never parses one
- No password env var in compose → never interpolated
- No password secret in helm → never mounted
- No password generated by deploy workflow → never rotated
- No password in client CONNECT frame → never observed on wire

Drift becomes **structurally impossible**. There is exactly ONE thing
that authenticates a service: its mTLS client cert. Rotate the cert,
rotate the identity. Atomic. Unambiguous.

### Why SSoT at services.yaml (not TS const, not JSON)

The repo's existing SSoT gold standard is `MODULE_SCHEMAS` in
`libs/backend-common/src/database/schema-manager.service.ts:79` — a
hand-maintained TypeScript constant with a MAINTENANCE CONTRACT
docblock, consumed by runtime + CI invariant test.

For NATS services, YAML was chosen over TS-const because:

- **Multiple non-TS consumers.** The generator script reads YAML via
  Python + PyYAML (ubiquitously available). The cert CN list (bash
  script) reads via grep. TS-const would require every consumer to
  spawn a Node process just to read the list.
- **Human-reviewable ACLs.** Subject allow-lists are inherently YAML-
  shaped (nested arrays). TS-const literal arrays add syntactic noise.
- **Schema-validated.** `infrastructure/nats/services.schema.json`
  (Draft-07 JSON Schema) enforces shape at CI time via Ajv — same
  pattern as other platform YAML sources.

### Why keep tenant_<uuid> clones / per-tenant NATS accounts out of scope

The current NATS auth model is per-service, not per-tenant. Every
tenant shares service accounts. Per-tenant NATS accounts would be a
separate architecture (decentralized creds, account isolation) with
different trade-offs; tracked as a future RFC, not in scope here.

### Why not auto-generate cert CN list from services.yaml now

The cert generation script currently hand-maintains the list in
lockstep, enforced by the CI invariant test. Auto-deriving would
require `yq` in the deploy VM (currently only `jq` is available), a
build-time artifact (generating the shell script from YAML), or
embedding YAML parsing in bash. All three are viable; the ROI vs.
the one-line-hand-edit-in-lockstep is low when a CI test already
catches drift. Tracked as BACKLOG-NATS-002.

## Consequences

### Positive

- Single source of truth: adding a service = edit services.yaml + run
  the generator + add to cert script (three-line change, CI validates).
- No password rotation, no password storage, no password leak risk.
- Deploy pipeline ~100 lines shorter (removed provisioning blocks).
- NATS container env ~40 lines shorter (20 removed env vars per
  compose variant).
- Helm secrets ~40 lines shorter (20 removed secret keys).
- Cold-start deploy log shows `NATS auth mode: mtls-cert` per service
  — audit trail of which auth path was selected is now in logs.

### Negative / risks

- **Dev environment coupling.** Dev uses `nats-tls.conf` (TLS
  disabled) + `nats-auth.conf` (auth disabled) and connects
  anonymously. If a future dev config enables auth without mTLS, it
  would need to fall back to user/pass — the client factory's
  `user-pass` mode handles this but would require explicit env vars.
  Documented in the factory's updated docblock.
- **Certificate rotation is harder than password rotation.**
  Operational cost: cert rotation requires regenerating per-service
  certs + restarting services. Operationally simpler than password
  rotation (which also required restart) but requires more tooling
  (OpenSSL). Automated via `generate-internal-certs.sh` + cron.
- **Cannot disable mTLS in emergency without also disabling auth.**
  If mTLS is disabled (nats-tls-enabled.conf unmounted), cert CN is
  not extracted → auth fails. To debug, operator must mount
  `nats-auth.conf` (disable-auth variant) AND accept cross-tenant
  access risk. Documented in the rollout runbook.

### Neutral

- `NATS_*_SVC_USER` / `NATS_*_SVC_PASS` env vars (internal deploy
  bookkeeping, not client auth) are preserved for now. Their
  consumption is being audited (BACKLOG-NATS-003); if nothing reads
  them, they'll be removed in a later commit.
