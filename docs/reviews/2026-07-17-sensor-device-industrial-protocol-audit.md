# Sensör Modülü — Endüstriyel Cihaz Yüzeyi + Protokol + Test Uçtan-Uca Audit

**Tarih:** 2026-07-17
**Kapsam:** `/sensor/devices` (edge controller + sensör + VFD ekleme akışları ve tüm alt sekmeler) — FE (`web/modules/sensor-module`) + BE (`apps/sensor-service`, `sens-api-gateway`, `apps/sensor-ingestion`), tüm endüstriyel haberleşme protokolleri ve test kapsamı.
**Yöntem:** 9 uzman ajan (6 cihaz-yüzeyi + 3 protokol/test) + her CRITICAL/HIGH bulgu için bağımsız adversarial doğrulama + bütünlük eleştirmeni. 48 ajan, ~3.84M token. REFUTED bulgular elendi; DOWNGRADE'ler doğrulayıcı verdict'ine göre düzeltildi.
**Standart:** Duplication yok · yama/susturma yok · sonraya bırakma yok · endüstri-seviyesi (IEC 62443 yazma-yolu güvenliği, mTLS kimlik, safe-state, golden-codec test). Her düzeltme CLAUDE.md tier hiyerarşisine göre önerildi (tier-1 yapısal imkânsızlık → tier-3 build/test-zamanı tespit).

## Yönetici özeti — sağlık değerlendirmesi

Bu yüzey **iki hızda** ilerliyor. 2026-07-05 audit'inin 28 bulgusunun ~24'ü gerçekten kök-nedenden çözülmüş (SSRF `SafeHttpClient`, tenant fail-closed, konum hiyerarşisi serialize, enum parity, hash'lenmiş provisioning key'leri) — sensör ve edge **happy-path**'i artık çalışıyor. Rust edge çekirdeği (Modbus rodbus+TLS+adres-aralığı yazma authz, LoRaWAN gerçek AES-CMAC MIC + DevNonce replay tablosu, OPC UA typed RBAC, ingestion sidecar'ın üç-kapılı tenant binding'i) **gerçekten endüstri-seviyesi**.

Ama platformun sattığı "endüstriyel güvenilirlik" iddiasını kıran **sistemik yalanlar ve güvenlik açıkları** var. En ağır üçü:

1. **VFD yazma yolu donanıma ulaşmıyor ama başarı raporluyor** — iki bağımsız kök-neden: (a) 7 VFD adaptöründen 6'sı frame kurup **iletmeden** `success:true` dönüyor; (b) manuel onay→uygula yolu tüketicisi olmayan bir olaya yayınlanıyor. Sonuç: Modbus-TCP dışı bir sürücüde **EMERGENCY_STOP "başarılı" der, motor (aeratör/pompa) çalışmaya devam eder → balık-ölümü riski.**
2. **~25 bulut protokol adaptörü stub ama sihirbazda seçilebilir** ve seçildiğinde sensör hiç temas kurulmadan `ACTIVE`/"connected" işaretleniyor — endüstriyel bir platformda sistemik ux-truth ihlali.
3. **Protokol kimlik bilgileri düz metin** saklanıyor ve gate'siz `sensors` sorgusuyla **her tenant kullanıcısına** yansıtılıyor.

**En kritik mimari karar (plan için):** Bulut'ta 40 TS adaptörü var (28'i stub), edge Rust'ta ~10 gerçek protokol var. Örtüşen protokollerde (modbus, mqtt, opcua, i2c/spi, lorawan) **üretim I/O yolu edge Rust gateway.** Bulut TS stub seti büyük ölçüde demo-ware. SSoT çözülmeli: ya (A) stub'ları tek `EdgeDelegatedProtocolAdapter` bildirimine indir, ya (B) tamamen kaldır. Ayrıca ingestion sidecar Rust-vs-Node hâlâ per-tenant **canlı çift-yol** çalışıyor.

**Rakamlar:** 3 CRITICAL · 27 HIGH · 56 MEDIUM · 16 LOW = **102 doğrulanmış bulgu**. Ek olarak: 63 protokol sınıflandırması, **41 test boşluğu** (17× P0), ~30 SSoT/merge fırsatı, ~30 eksik yetenek.

### Tema bazında yoğunluk
- **ux-truth / sahte-başarı (en büyük küme):** stub adaptörler, sahte VFD yazma, sahte "canlı" telemetri, koşulsuz yeşil config-push, kalibrasyon durumunun asla yazılmaması, mock cihaz seçicisi, ölü butonlar.
- **ics-safety:** motor-çalışırken yazma (fail-open `isMotorRunning`), FAULT-durumu interlock yok, S7 placeholder bytecode'un gerçek PLC'ye download'u, non-idempotent apply.
- **duplication / SSoT:** 3 sihirbaz + 4 step-machine, 5 özel raw-fetch GraphQL client, 3× parametre kataloğu (çelişen birim/aralıklar → alarm eşiği kayması), 2 zaman-serisi deposu, 2 audit ledger, çift RiskLevel enum, GraphQL codegen yokluğu.
- **tenant-isolation / güvenlik:** düz-metin kimlik bilgileri, SSRF guard'ının yalnızca 4 adaptörü kapsaması, tenant-context'siz otonom 30sn donanım yazıcısı, edge io_data/alarm'ın tenant şeması olmadan yazılıp sessizce düşmesi.
- **test:** 39+6 adaptörde sıfır adaptör-testi, güvenlik-kritik yazma/safe-state yollarında sıfır test, e2e cihaz suite'lerinin CI'da hiç koşmaması, sihirbazlarda sıfır FE testi.

## SSoT / birleştirme (merge) yol haritası

Aşağıdakiler "birleşebilecek kısımlar" — her biri tek bir sahip (SSoT) altında toplanmalı. Duplication kaynı kavramın 2+ yerde, çoktan **davranışsal olarak sapmış** kopyalarıdır (çelişen birim/aralık, çelişen alan adı, çelişen validasyon).

**FE — cihaz yüzeyi:**
1. **Tek sihirbaz çatısı** — 3 sihirbaz (sensör/VFD/edge) + 2 ölü step-machine → tek `wizard/` (modal shell + stepper + step-validation + dirty-close guard + draft store). Bugün stepper/backdrop/footer/reset/submit-lock 3× kopyalanmış ve zaten sapmış (connection-test zorunlu vs opsiyonel).
2. **Tek GraphQL client** — 5 özel raw-fetch wrapper + `useDataChannelList` → `config/api.ts`'in `graphqlFetch`'i (paylaşılan `graphqlClient`). Token-lifecycle/401-retry/tenant-propagation **bir kez** var olmalı; wrapper'lar tam da öldürülmek istenen 401-race'i geri getiriyor.
3. **Tek cihaz-detay çatısı** — 3 detay sayfası (Edge 2139 sat., Sensör 731, VFD 155) → cihaz-tipi-eklentili tek çatı. Her cross-cutting düzeltme (rol gating, staleness badge, ack indicator, i18n) bugün 3× yazılıyor.
4. **Tek VFD katalog kaynağı** — FE-static marka/protokol/model/config kataloğu → backend `vfdProtocolSchema` sorgusu (zaten var, sonucu atılıyor) + `DynamicFormRenderer`. Protokol-config şekli 3-4 yerde ve 2 protokole (EtherNet/IP, PROFIBUS_DP) çoktan tamamen kırık halde sapmış.
5. **Tek Modal primitifi** (`shared-ui`) — 6 elle-yazılmış modal (focus-trap yok, WCAG hatası).
6. **GraphQL codegen** — 28 elle-yazılmış operasyon + ~100 elle-tutulmuş mirror tipi → supergraph SDL'den generate. Drift'i compile hatasına çevirir; ölü `sensorRegistrationApi.ts` (22 op) kataloğunu ve enum/alan sapma sınıfını **tek hamlede** kapatır.

**BE — sensör/VFD:**
7. **Tek sensör yazma yolu** — `sensor/` (createSensor, updateSensor, sensorRawList) → `registration/` (doğru quota/validasyon/lifecycle/event sahibi). İki yol çelişen invariant'larla quota-bypass ve event-görünmezliğinin kök nedeni.
8. **Tek parametre/kanal kataloğu** — 3 kod-içi `KNOWN_PARAMETERS` kopyası (water_level cm-500 vs m-10; co2 mg/L-100 vs ppm-5000 çelişiyor — **alarm eşiğini besleyen güvenlik-ilgili veri bölünmesi**) → DB-backed `SensorTypeDefinition`/`industry_templates`.
9. **Tek kanal modeli** — child `Sensor` satırları + `SensorDataChannel` → `SensorDataChannel`. Bir "kanal" bugün hangi akışın yarattığına göre iki farklı entity.
10. **Tek zaman-serisi deposu** — `sensor_readings` (JSONB) + `sensor_metrics` (EAV) → tek kanal-anahtarlı depo; `MetricQueryService` (ölü) bağlanmalı. Cihaz sayfaları yalnızca `sensor_readings` okuyor, edge-ingest kanal verisi görünmez.
11. **Tek kanal-öneri hattı** — `ChannelDiscoveryService` (sezgisel) + `ChannelDetectionService` (AI) → tek hat, maturity flag'li.
12. **Tek VFD audit ledger** + **tek register read/parse/scale** — iki ledger ve write/read yollarında ayrık byte-order/scaling → tek immutable trail + paylaşılan codec.
13. **Tek cross-schema cihaz lookup** — `findDeviceAcrossSchemas` + `scanDeviceAcrossSchemas` + `mapRowToEdgeDevice` → `DeviceDirectoryService`.
14. **Tek ingestion yolu** — Rust sidecar vs Node/TS çift-yolu çözülmeli (per-tenant canlı çift-yol şu an SSoT ihlali).

## Eksik yetenekler (endüstri-seviyesi için gerekli, kod'da yok)

**Güvenlik/lifecycle:** cihaz `REVOKE` transition'ı (durum guard'lı ama mutation yok) · mTLS cert-based cihaz kimliği (ADR-015 yönü; entity'de kullanılmayan `certificate_*` kolonları var) · provisioning-key rotation (yalnızca create/revoke var) · enrollment preflight (gerçek zero-touch için).

**VFD/kontrol güvenliği:** dağıtık DB-backed idempotency + per-drive serializasyon (bugün yalnızca in-memory flag) · canlı-sürücü hazırlık/interlock preflight (fault/running/comm-loss/remote) · derlenmiş automation programlarının deploy-öncesi safety validasyonu (bounds/loop/actuator-conflict) · risk-tier'a orantılı step-up/four-eyes yetki.

**Sensör/kalibrasyon:** kod-deploy'suz per-tenant özel protokol/payload mapping (self-serve'ün çekirdeği; `SensorProtocol.configurationSchema`/`dataMapping` yüzeyi var ama executor yok) · kalibrasyon workflow'u (event + actor + referans standart + due/overdue + drift; `calibration/` şu an 3 sıfır-byte dosya) · toplu cihaz import/fleet onboarding (bugün tek-tek sihirbaz) · connection-test yüzeylerinde rate-limit · sensör decommission lifecycle (bugün hard-delete → yetim reading) · per-tenant referans-data seed migration mekanizması.

**Operate/maintain (bütünlük eleştirmeni):** firmware/OTA gerçek yüzeyi (FE `FirmwareManagementCard` var, backend `getAvailableFirmwareVersions()`=[] döndürüyor; gerçek imzalı `release-bundle`/`deploy-artifact` yolunun FE'si yok) · cihaz health/heartbeat offline alerting (edge stale-sweep sessizce OFFLINE'a çeviriyor, event/alarm yok; sensörlerde offline tespiti hiç yok — **balık-ölümü güvenlik hikâyesinin çekirdeği**) · FE↔BE kontrat-parity + wizard→DTO invariant testleri · cihaz-lifecycle domain event'leri (Vfd/EdgeDevice Registered/Decommissioned — bugün hiç event yok, alert-engine/farm-service için cihaz lifecycle görünmez).

### SENSOR-LOW-024 — Swallowed errors convert partial failures into full success on write paths
- **Alan / kategori:** BE·Sensör kataloğu · `ics-safety`
- **Kanıt:** `apps/sensor-service/src/sensor/resolvers/sensor.resolver.ts:268-273 — createSensor catches channel-bootstrap failure, logs warn, returns success`; `apps/sensor-service/src/device-group/services/device-group.service.ts:259-267 — addMembers catches the bulk save error ('Some members may already exist'), re-fetches, and returns the member list as if the add succeeded — a genuine FK/constraint failure is indistinguishable from a duplicate`; `apps/sensor-service/src/protocol/services/protocol-registry.service.ts:48-50 — adapter resolution failure at boot logs a warn and silently shrinks the protocol catalog`
- **Sorun:** Three catch blocks turn real failures into success signals. The device-group case is user-visible: an operator adds 10 devices to a group, the save fails midway (TypeORM save of an array is not atomic), and the mutation returns the current member list with no error — devices the operator believes are grouped (and will receive group batch operations) are not.
- **Kök-neden düzeltme:** device-group: insert members in one transaction with ON CONFLICT DO NOTHING for the duplicate case, rethrowing anything else. createSensor: resolved by the write-path merge (channels join the registration transaction). protocol registry: fail startup on adapter resolution failure — a silently smaller catalog is schema drift.

### SENSOR-LOW-025 — Change-set rollback writes a literal 0 to safety registers when the original previousValue is null
- **Alan / kategori:** BE·VFD kontrol · `ics-safety` _(doğrulayıcı: HIGH→LOW)_
- **Kanıt:** `apps/sensor-service/src/vfd-programming/services/vfd-change-set.service.ts:454-465 — inverse item is created with requestedValue: item.previousValue ?? 0`; `The inverse change set is then submitted/auto-approved and applied by VfdParameterWriterService, which reverse-scales and writes requestedValue to def.registerAddress`; `previousValue is only populated during a successful apply read-back (vfd-parameter-writer.service.ts:94); items that failed before read-back, or rolled-back items, can carry null`
- **Sorun:** rollbackChangeSet builds an inverse change set by swapping requestedValue↔previousValue, but coalesces a null previousValue to 0. If the original apply never captured a baseline (e.g. read-back failed, or an emergency rollback of a partially-applied set), the rollback commands 0 to registers such as max_frequency, current_limit_percent, or a control word — a hazardous value delivered under the label 'rollback'. Range validation is not re-run on the inverse set before write.
- **Kök-neden düzeltme:** Never fabricate a rollback target. If item.previousValue is null, exclude that item from the inverse set and surface it as an un-rollbackable parameter requiring manual attention, rather than writing 0. Re-run validateValueInRange on every inverse item against the current parameter definition before the inverse set can be applied.

### SENSOR-LOW-026 — writeParameterValue is an unbounded direct-write primitive with no server-side clamp against brand-config limits
- **Alan / kategori:** BE·VFD kontrol · `security`
- **Kanıt:** `apps/sensor-service/src/vfd-programming/services/vfd-parameter-writer.service.ts:158-166 — writeParameterValue reverse-scales and writes value with no min/max validation`; `Range validation lives only in VfdChangeSetService.validateValueInRange, applied at addItems/submitForApproval (vfd-change-set.service.ts:133-138,216-221) — the apply moment and this direct primitive do not re-check`; `Grep for writeParameterValue callers: no resolver invokes it (dead but public write surface)`
- **Sorun:** writeParameterValue can push an arbitrary engineering value straight to a register with no bounds check; it is a public method currently unused by resolvers. Even on the change-set path, values are validated only when added, not re-clamped at the instant of write, so a definition change between submit and apply is not re-enforced. This leaves an unguarded write primitive one wiring mistake away from an unclamped hardware write.
- **Kök-neden düzeltme:** Centralize a single clampAndWrite(def, value) that enforces def.minValue/maxValue (and isWritable) immediately before every register write, used by both applyChangeSet and writeParameterValue. Remove writeParameterValue if it has no caller, or gate it behind the same validation + audit as the change-set path.
