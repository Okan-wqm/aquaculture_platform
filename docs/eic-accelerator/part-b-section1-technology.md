## 1. TECHNOLOGY

### 1.1 Novelty and breakthrough nature

**Status first.** ARIA is a repository-resident maintenance system for one multi-service code base, the applicant's own production platform. Until its runtime was paused on 16 October 2026, its cycles ran 15 registered code detectors, had language-model agents judge their output, recorded their state in hash-chained ledgers and planned changes through adversarial cross-review between agents. The runtime has been paused since that date. Every figure below about its live behaviour was recorded between 5 August and 16 October 2026, when it started 90 cycles and completed 71 (n = 90).

We keep three kinds of result apart. An ARIA runtime result was produced by ARIA's own cycles before the pause. An offline measurement was made by us on ARIA's code or prompts. Engineering is work by people and AI-assisted coding sessions. ARIA's code is not written by ARIA: of the commits touching its code from 1 June to 26 October 2026 (merge commits included), 1,464 carry the one git identity shared by the team and its AI sessions, 84 a session identity (in two spellings) and 0 the account ARIA's own implementer uses.

**What we claim is new.** Our starting position is that regulated and critical software needs maintenance with an audit trail, in which each claim an agent makes can be checked. Our proposition is verifiable autonomy, built from four elements:

1. _An evidence law._ An agent output is admitted only if the code it cites can be checked against the repository. Until the pause, 59 of 833 agent results (7.1%) were rejected under this law, 347 belief candidates for ARIA's memory were refused (289 matched more than 500 files, 58 matched none), and 1,382 of 2,313 requests were refused as stale instead of being answered on an expired snapshot.
2. _Hash-chained records._ 71 ledger files with 63,331 rows show no broken chain. The chains are not signed, and the records do not separate ARIA's acts from operator acts, so they show internal consistency, not authorship.
3. _Adversarial cross-review._ Of 42 plans started, 18 reached convergence; 69 of 92 cross-reviews raised material risks. Convergence is not plan quality.
4. _Independent examination and gates fixed in advance._ A board outside ARIA's trust domain would examine ARIA's changes to itself and sign its verdicts, and pass criteria are written down before any measurement. The board is a design, not a system: only one part, a derived list of files ARIA may never write, is merged and tested (built and tested, not yet measured). The identity and sealed-vault package is an open, unmerged pull request awaiting the operator's signature, and the examination runner has no code.

**Is it deep tech, and what we do not claim.** The elements use known primitives (hash chains, exact statistical tests, model-based review); the contribution we propose is their combination in an agent whose outputs are bound to checkable evidence and whose own changes are examined from outside. We do not claim a cost or performance advantage over existing or alternative solutions: it has not been demonstrated, and our own pilot points the other way (Table 1). "Evidence-bound" today means that the cited file exists at the named commit; 0 of 2,364 sampled findings carry a quoted excerpt showing that the cited text supports the claim. A quote law is built and tested, not yet measured, and has not been applied to live findings.

**What the data taught us, and the disruptive potential.** The pilot and the planted-defect test show that the finding layer, not the judging layer, is the weak part. The next phase is therefore built around a language model reviewing one named change, with ARIA's rules as a cheap pre-filter. Built and tested, not yet measured: the single-change entry, the explicit change context passed as escaped untrusted data, and a per-change budget are merged; the step that turns reviews into defect hypotheses is still being built; no workflow invokes the mode and it has 0 live runs.

Whether the approach disrupts existing solutions is untested. We have not yet compared ARIA with a plain language model on real regressions. The comparison is pre-registered: 35 verified real regressions and 120 clean controls; ARIA's recall must exceed both a plain-model arm and a three-reviewer arm, at one-sided exact McNemar p < 0.05 against each, without more reports per clean commit. 0 of the 35 cases have been run. It will be run once, on a sealed held-out set, on [DATE]. With 35 cases the test has little power, and our pilot suggests the plain arm will be strong; if ARIA does not win, we will publish the result and rest the claim on verification, not discovery.

### 1.2 Technology Readiness Level (TRL)

**Our assessment.** We do not assert that all aspects of TRL 5 (validation in a relevant environment) are completed for the system as a whole. We assess the maintenance pipeline (find, judge, plan, implement, pull request) at TRL 4 as a whole, because its find stage has not been validated against its requirement, and at TRL 5, lower end, for the plan-to-pull-request segment on n = 1. We claim TRL 6 for no component. An evaluator who weighs the single instance lightly should read the pipeline as TRL 4.

**The relevant environment** is the applicant's production monorepo: 17 backend applications (15 services, a Rust sidecar and a migration tool), React front ends and a Rust gateway, with real continuous integration, required checks and code owners. It is a real setting, but it is one repository, written by the applicant, with ARIA's own code inside it: no second team, customer code base or external user.
