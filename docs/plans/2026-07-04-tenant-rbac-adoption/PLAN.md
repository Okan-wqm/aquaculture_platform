# Tenant-Managed Fine-Grained RBAC — Platform Adoption Master Plan

**Date:** 2026-07-04
**Status:** Draft for architectural-arbiter review
**Scope:** Platform-wide (NestJS microservices `apps/`, React microfrontends `web/`, Rust edge `sens-api-gateway/`, offline PWA `web/apps/aquamobil`)
**Program tracking:** `docs/reviews/` finding IDs referenced per phase; every fix commit carries a `Closes:` line.

## Problem statement

The platform has **built, wired, and shipped** a complete fine-grained, tenant-managed RBAC subsystem — tables (`auth.tenant_roles`, `auth.tenant_role_permissions`, `auth.user_role_assignments`), a live auth-service read/write path (`apps/auth-service/src/modules/tenant/services/tenant-role.service.ts`), a JWT projection (`token.service.ts:548-621`), an effective-permission guard (`libs/backend-common/src/guards/tenant-permission.guard.ts`), and a functional tenant-admin editor UI (`web/modules/tenant-admin/src/pages/TenantRolesPage.tsx`) — and then **enforced it on effectively zero endpoints**. The five `@RequireTenantPermission('edge:manage-io-config')` decorators on `apps/sensor-service/src/edge-device/edge-device.resolver.ts:342-458` are *dead metadata*: no guard consuming `REQUIRED_TENANT_PERMISSIONS_KEY` is registered as an `APP_GUARD` in any service, and `resourcePermissions` is silently dropped at the gateway's verified-user-assertion boundary before it ever reaches a subgraph. The permission string they reference is not even in the catalogue. Measured across the 7 tenant-scoped services there are **~944 tenant-data GraphQL operations** (farm 435, sensor 283, hr 155, messaging 45, alert 19, hydroponics 6, ai 1); fine-grained RBAC gates **5** of them and even those 5 are actually enforced only by their co-located `@Roles` decorators. Current adoption is **~0.53%**. Meanwhile **three parallel authorization models** and **five parallel guard/decorator stacks** coexist, with a fixed 4-role enum (`libs/backend-common/src/decorators/roles.decorator.ts:16-62`, 815+ `@Roles` usages across 93 files) as the *only* model actually enforced. This is a build-vs-adoption gap, not a build gap. This plan drives that gap to 100% enforcement of tenant-data endpoints on the fine-grained model — with zero user lockout, zero downtime, root-cause-only fixes, and an invariant that makes regression structurally impossible.

## Executive summary

**Verdict:** The correct move is *adoption and consolidation*, not new construction. The fine-grained subsystem is architecturally sound; it is un-enforced, un-propagated (claim dropped at the gateway), un-complete (catalogue covers ~30 of ~800 resources), and shadowed by two dead/legacy models plus orphaned duplicates. Every dimension below is a wiring, consolidation, backfill, or invariant task — not a green-field build.

**The three-model consolidation target (collapse A + B + C → ONE):**

- **(A) Fixed global 4-role enum** — `Role: SUPER_ADMIN > TENANT_ADMIN > MODULE_MANAGER > MODULE_USER` (`roles.decorator.ts:16-62`). **Retained** as a *coarse platform-role floor* (defense-in-depth) and for genuinely platform-scoped/tenant-lifecycle operations, but demoted from primary gate to secondary floor for tenant-data endpoints. `@Roles` is **kept, not deleted** (a lint forbids *new* tenant-data endpoints relying on `@Roles` alone).
- **(B) Fine-grained tenant RBAC** — `resource:action` permissions stored per-tenant in `auth.*`, projected into the JWT `resourcePermissions` claim, enforced by a single map-driven guard. **Becomes the platform default** for every tenant-data operation across all 7 tenant-scoped services.
- **(C) Legacy `shared.user_permissions`** — per-user camelCase `PanelPermissions` blob. **Deleted** after its per-user customizations are folded into `auth.user_role_assignments.permission_overrides`.

**Plus the dead surfaces retired:** the orphaned duplicate `apps/admin-api-service/src/users/services/tenant-role.service.ts` (registered in no module), `RoleTemplateService`'s static fictional templates + the never-created `tenant_custom_roles` write path, the dead gateway `PermissionGuard` stack, and the dead OPA authz scaffolding — all deleted so exactly one live authorization SSoT remains.

**The one target model in one sentence:** a single fail-closed, transport-agnostic authorization pipeline — **Plan-entitlement ceiling ⊇ Module-assignment scope ⊇ Fine-grained tenant permission**, composed with **AND** semantics beneath a coarse `@Roles` floor — driven by ONE typed permission catalogue SSoT, projected through the JWT and the HMAC-bound federation assertion, enforced identically on REST, GraphQL (operation + field), WebSocket, and service-to-service, and rolled out through a tri-state `off | observe | enforce` mode with a monotonic adoption ratchet that burns down to 100%.

## Target architecture

### The ONE model and how coarse + fine compose

For any request to a tenant-data operation, authorization is the conjunction of independent gates evaluated in a fixed order. A granted fine-grained permission is **necessary but never sufficient**: it cannot exceed the tenant's plan entitlement, cannot reach a module the tenant/user is not assigned, and sits beneath a coarse role floor.

```
Request
  │
  ├─(1) ServiceIdentityGuard      — mTLS/HMAC service-principal identity (verifiedIdentity)   [APP_GUARD #1]
  ├─(2) Gateway AuthGuard         — RS256 JWT verify + per-user not-before (isValidToken)      [gateway only]
  ├─(3) TenantGuard               — tenant context resolution + isolation                      [APP_GUARD #2]
  ├─(4) RolesGuard                — coarse @Roles hierarchy floor (defense-in-depth)           [APP_GUARD #3]
  ├─(5) EntitlementGuard          — plan-tier ceiling (PLAN_CATALOG capability/quota)          [outer ring]
  ├─(6) ModuleAccessGuard         — tenant_modules.isEnabled ∧ user_module_assignments.isActive
  ├─(7) TenantAuthorizationGuard  — fine-grained resource:action, map-driven, fail-closed      [APP_GUARD #4]
  │        └─ mode: off | observe(shadow, fail-open) | enforce(fail-closed)
  └─(8) PermissionCoverageGuard   — fail-closed default: any tenant-data mutation with neither
                                     a mapped permission nor an explicit escape → 403
```

**Composition rule (precedence):** `Plan ⊇ Module ⊇ Permission`, all AND-composed, all fail-closed, beneath the coarse `@Roles` floor. `SUPER_ADMIN` bypasses everything (god). `TENANT_ADMIN` bypasses the fine-grained check (tenant owner / role-manager) — centralized in a single `isTenantSuperuser(user)` predicate that **emits an audit event on every bypass** and is **suppressed inside an impersonation context**.

### Request → guard → claim → DB flow (end-to-end)

1. **Login / refresh (auth-service).** `token.service.generateTokens` resolves the user's **effective** permission set = `role.resource_permissions` merged with `user_role_assignments.permission_overrides` via the single canonical `computeEffectivePermissions` (revoke-wins), for an **active AND non-expired** assignment. SUPER/TENANT_ADMIN carry `['*']` (mobile) / no fine-grained claim (backend, bypass by hierarchy). The set is projected into the RS256-signed JWT `resourcePermissions` claim (renamed `effectivePermissions` if the S3 decision is ratified), inline within a byte budget or as an epoch-keyed reference blob when oversized. `planLevel` and `modules` claims ride alongside.
2. **Gateway.** `AuthGuard` verifies RS256 (kid+aud+iss) and enforces the per-user not-before (`isValidToken(jti, sub, iat)` against a durable `auth.users.authz_version` mirrored to Redis) so a permission change revokes stale tokens within seconds. The gateway builds the **HMAC-bound verified-user assertion** carrying `roles`, `resourcePermissions`, `modules`, `planLevel`, `assignedSiteIds`, `mobileFeatures` — tamper-proofed by the existing `X-Service-Assertion-Hash` (no signing-format change). If the claim was reference-form, the gateway resolves it from the epoch-keyed Redis blob and injects it before forwarding.
3. **Subgraph.** `verified-user-assertion.middleware` rebuilds `req.user` from the HMAC-verified assertion (never re-querying auth on the hot path). The guard chain runs: coarse `@Roles` floor, then `EntitlementGuard` (plan), `ModuleAccessGuard` (module), then `TenantAuthorizationGuard` derives the required permission from `info.fieldName` via the per-service `OPERATION_PERMISSIONS` map and checks it against `req.user.resourcePermissions` (SUPER/TENANT_ADMIN bypass, audited). `PermissionCoverageGuard` fail-closes any unmapped tenant-data mutation.
4. **DB.** The permission set originated from `auth.user_role_assignments → auth.tenant_roles → auth.tenant_role_permissions` (raw SQL, tenant-scoped by `tenantId`, defense-in-depth RLS on the `auth.*` RBAC tables). Row-level tenant isolation is enforced at the database layer beneath the hand-written `WHERE tr."tenantId" = $x` predicates.

### Data model (target)

- **Exactly one store:** `auth.tenant_roles` (+ `auth.tenant_role_permissions` authoring/projection pair) + `auth.user_role_assignments` (unique on `user_id` → one active role per user + per-user `permission_overrides {grants,revokes}`), all in schema `auth`, owned by auth-service, drift-tested against one canonical persistence-entity set.
- **`code`** adopted as the stable machine identifier for `is_system` roles; the dead `auth.tenant_roles.permissions` jsonb column dropped; `panel_permissions` jsonb retained as the authoring mirror, `resource_permissions text[]` as the enforced projection.
- **Denormalized `tenant_id`** added to `tenant_role_permissions` and `user_role_assignments` (blue-green nullable → backfill → NOT NULL) so DB-native RLS is structurally possible.
- **`auth.users.authz_version integer NOT NULL DEFAULT 0`** — durable per-user revocation epoch.
- **`admin.system_role_templates`** — platform-owned, versioned default-role templates (SUPER_ADMIN editable) that `seedDefaultRoles` stamps into new tenants.
- **`auth.rbac_change_approvals`** — maker-checker pending queue for sensitive grants (two-person integrity), `CHECK(approver_id <> requester_id)`.

### JWT projection

`resourcePermissions` (or `effectivePermissions`) carries the **override-resolved, expiry-aware** effective set. `permission_overrides` finally enters the token (today `computeEffectivePermissions` is display-only). The 60s per-pod mint cache is replaced by an **epoch-keyed Redis blob** `authz:effperm:<userId>:<authz_version>` so a version bump structurally invalidates it platform-wide. Claim size is bounded by an inline byte budget with a gateway-resolved reference fallback. RS256 kid/aud/iss discipline is unchanged.

### Guard contract (one decorator family, one guard family)

- **Map-driven primary:** per-service `src/common/authz/operation-permissions.ts` exporting `OPERATION_PERMISSIONS: Record<OperationName, Permission[]>` (tenant-data ops) and `PLATFORM_ROLE_OPERATIONS: Record<OperationName, Role[]>` (coarse escape hatch for tenant-lifecycle/platform-admin ops). `TenantAuthorizationGuard` derives the requirement from `info.fieldName`; unmapped op → fail-closed 403.
- **Optional inline override:** `@RequirePermission(...ids: PermissionId[])` / `@RequireAnyPermission(...)` where `PermissionId` is a **compile-time union generated from the catalogue** — an off-catalogue string is a type error. `@RequireTenantPermission` aliased to `@RequirePermission` for one release.
- **Explicit escapes:** `@PlatformRoleOnly()`, `@Public()`, `@AllowServiceIdentity(callers)` — a service principal reaching a permission-gated handler is denied unless allowlisted.
- **Field-level authz** uses the same decorator on `@ResolveField`.

### Mobile (aquamobil)

Gates every surface (routes, tabs, hub CTAs, per-action mutation buttons) off the **same server-computed effective set** delivered on the identity query (`effectivePermissions` + coarse `mobileAccessEnabled`). The 12-flag `allowedFeatures` model is retired as an authz source (the coarse `isMobileEnabled` device toggle is retained). The client role-floor stack (`role-rank.ts`, `meetsRoleFloor`, `FEATURE_ROLE_FLOOR`) is deleted; privilege lives in the permission (`harvest:record` granted only to designated roles reproduces the old MODULE_MANAGER floor as *data*). Admins carry a `*` wildcard so the client needs no role special-casing. A typed `FEATURE_PERMISSIONS: Record<MobileFeature,{reach,act?}>` map gives compile-time exhaustiveness; offline cache holds the permission set + server version for revocation-aware invalidation.

### Frontends

`tenant-admin` becomes the single complete control plane (role CRUD + per-user Access drawer with grants/revokes overrides, expiry, accessType, server-computed effective preview), consuming the codegen'd GraphQL SSoT so backend contract drift is a compile error. `admin-panel`'s dead `RoleManagementPage` is repurposed into a **platform RBAC console** (read-only catalogue view, system-role-template CRUD, cross-tenant adoption/drift observability) — same route, real data, no write path into any tenant's roles. All FE gating moves from role-matrix to permission-set gating driven by the JWT claim, in lockstep with backend matrix removal.

## Canonical permission taxonomy

**SSoT location:** a new bounded library **`@platform/authz-contracts`** (mirroring `@platform/event-contracts`, FE-importable without pulling `backend-common`), physically at `platform/libs/authz-contracts/src/permission-catalog.ts`. `libs/backend-common/src/authz` and per-service maps re-export from it. This resolves the three-way home conflict (S2 vs S4/S8) in favor of the FE-importable dedicated lib.

**Format decision (must be ratified in Phase 0a, pinned by a regex invariant):** **3-segment `domain:resource:action`** lowercase-kebab (e.g. `farm:tank:create`, `sensor:vfd:command-start`, `hr:payroll:view`, `billing:subscription:view`). Domain-qualification makes cross-service name collisions a compile/regex impossibility (`equipment` in farm vs hr, `sites`, `shifts` no longer globally ambiguous). Because every downstream dimension (S1 maps, S3 token, S4 seeds, S7 mobile) currently authors 2-segment strings, this decision is a hard Phase-0a gate; a `LEGACY_ALIAS: Record<2seg, PermissionId>` + dual-accept/dual-emit window + one-time backfill migration converts stored grants without lockout.

**Shape:**

```ts
type PermissionDef = {
  id: PermissionId;               // domain:resource:action
  domain: Domain;                 // one of 8 tenant contexts + billing(read-only) + reports
  resource: string;
  action: string;
  description: string;
  class: 'read' | 'write';
  uiGroup: string;                // decoupled from domain; defaults to domain
  requiresEntitlement?: keyof PlanLimits;   // outer-ring plan ceiling binding (S11)
  requiresModule?: string;                  // outer-ring module binding (S11)
};
export const PERMISSION_CATALOG = [ /* ... */ ] as const;
export type PermissionId = typeof PERMISSION_CATALOG[number]['id'];
```

`PermissionId` is a generated string-literal union (make-it-impossible). `isPermissionId()` runtime guard for trust-boundary inputs. `expandPermissions(granted): Set<PermissionId>` is the **single** wildcard-expansion SSoT (grammar: `domain:resource:*`, `domain:*:*`, reserved `*` for platform-super only); wildcards are authoring sugar, canonical storage is concrete expanded ids.

**Category / resource / action tree (must be exhaustive across all 8 tenant-data domains + read-only billing + reports):**

- **farm** — sites, departments, systems, tanks, ponds, equipment, batches, species, mortality, cull, growth, harvest, feeding, water_quality, maintenance, transfer, storage/stock, tasks, regulatory, weather, sentinel-hub, purchase-order/inventory, supplier, chemical, consumable, spare_parts, site-contacts. Actions: view/create/edit/delete + named capabilities transfer/split/merge/plan/record/harvest/approve/manage_schedules/manage_inventory.
- **sensor** — sensor, sensor-type, calibration, dashboard-layout, device-group, protocol, automation-program; **edge** (manage-io-config, set-digital-output, scan-hardware, lora-manage); **vfd** (device CRUD, command-start/stop/set-frequency/emergency-stop, automation, programming approve/rollback, reading); **plc** (connection, opcua-write/method, feeding-parameter, alarm-acknowledge/escalate); **process/scada** (deploy-to-edge, package CRUD); **scada-ws** (tag-write, alarm-ack).
- **hr** — employee, department, attendance (view/record self-service), leave (view/request/approve), shifts/scheduling/rotations, payroll (view/manage), performance/goals, training/certifications, worker.
- **hydroponics** — configuration (CRUD), grow-cycle.
- **alert** — rule (CRUD), escalation-policy, suppression-window, on-call, acknowledge, resolve, receive-critical (notification-target predicate).
- **messaging** — channel, message (send/edit/delete/pin/forward/react), presence, gdpr (anonymize/export), ai-setting/consent.
- **ai** — agent, conversation, chat, tool, cost (view), safety.
- **reports** — per-domain report:view/export/create-custom.
- **billing** (read-only) — subscription:view, invoice:view (finance-viewer role; all write stays TENANT_ADMIN-only, no catalogue id).
- **mobile** (target) — the 12 mobile surfaces expressed as catalogue permissions (mortality:record, cull:record, harvest:record, feeding:record, water_quality:record, tanks:view, shifts:view, attendance:record, leave:request, tasks:view/complete, batches:transfer, stock:view/move).

**Naming convention:** standardize on the 3-segment kebab grammar; the current catalogue's snake_case actions (`manage_schedules`) and the ad-hoc kebab (`edge:manage-io-config`) both re-home to `domain:resource:action` (`sensor:edge:manage-io-config`). Enforced by regex: `^[a-z]+(-[a-z]+)*:[a-z0-9]+(-[a-z0-9]+)*:[a-z0-9]+(-[a-z0-9]+)*$`.

**Sync invariant (the SSoT guarantee):** CI asserts (a) every `@RequirePermission`/`@RequireTenantPermission` argument ∈ catalogue; (b) every `OPERATION_PERMISSIONS` / farm `permission-matrix.ts` operation and every reflected `@Mutation`/`@Query` maps to ≥1 catalogue id (completeness, with an explicit role-only allowlist); (c) catalogue ids unique + match the regex + `class ∈ {read,write}`; (d) exactly ONE catalogue literal exists (grep-guard forbids a reintroduced `PERMISSION_CATEGORIES`); (e) FE generated enum === BE catalogue (byte-set equality); (f) `LEGACY_ALIAS` keys are valid pre-migration strings, values ∈ catalogue. Adding a catalogue entry follows an ADR + architectural-arbiter gate analogous to the shared-schema-table W5 gate.

## Phased roadmap

The ordering follows the completeness critique's `recommendedPhaseOrder`. **No existing user is ever locked out** because: (1) the guard defaults to `observe` (fail-open shadow) until a service's gate proves 0 unexpected denies; (2) every legacy-enum user is backfilled a tenant-role assignment whose permission set ⊇ prior access *before* any enforce flip; (3) a token re-mint is forced before each flip; (4) the enforce flip is one hot config-service write per service, instantly reversible to `observe`.

### Phase 1 — Anti-lockout backfill

**Goal:** every existing non-SUPER_ADMIN user holds a tenant-role assignment whose permissions ⊇ prior access.
**In-scope:** seed 3 system roles per tenant (`SYS_TENANT_ADMIN`/`SYS_MANAGER`/`SYS_MEMBER`, keyed by `code`) + keep the 5 editable starter roles; expand `DEFAULT_ROLE_PERMISSIONS`. ## Backward-compatibility & zero-downtime migration

**Existing-user fixed-enum → seeded tenant-role backfill (the anti-lockout linchpin).** Today most `auth.users` have a `role` enum but no `user_role_assignments` row, so `getUserResourcePermissions` returns `[]` for MODULE_MANAGER/MODULE_USER — the instant enforcement flips they would 403 on everything. Phase 1 seeds 3 system roles per tenant and backfills every active non-SUPER_ADMIN user an assignment mapped from their enum (`MODULE_USER→SYS_MEMBER`, `MODULE_MANAGER→SYS_MANAGER`, `TENANT_ADMIN→SYS_TENANT_ADMIN` + bypass), with `resource_permissions ⊇` the enum's pre-migration access (proven by the no-lockout parity test derived from the old `MUTATION_ROLES`/`QUERY_ROLES` snapshot). SUPER_ADMIN/TENANT_ADMIN keep the guard bypass and are never at risk.

**Nullable → backfill → NOT NULL (every schema change is blue-green).** `auth.users.authz_version` is a Postgres fast-default add (no rewrite). `tenant_id` on `tenant_role_permissions`/`user_role_assignments` is added nullable, backfilled from the owning `tenant_roles` row, then flipped NOT NULL only after verification. `admin.system_role_templates` is nullable → backfilled from current defaults → NOT NULL. RLS is enabled additively beneath the existing application `WHERE` predicates so a momentarily-permissive policy breaks nothing. All down-migrations are forward-only for topology convergence (matching the existing `1800500000000` pattern).

**Format migration (2-seg → 3-seg) without lockout.** `LEGACY_ALIAS` is shipped first; `expandPermissions()` and token minting **dual-accept and dual-emit** both forms during the window, so a role granting `tanks:create` still authorizes `farm:tank:create`. A one-time idempotent data migration rewrites stored `resource_permissions` arrays to canonical ids. Write-boundary catalogue validation is enabled only *after* the backfill (else admins editing a legacy role would be blocked). The alias acceptance and dual-emit are removed only after ≥ one refresh-token lifetime (≤15m) plus margin, once all stored arrays are canonical. `edge:manage-io-config` has zero live grants, so its re-home needs no alias.

**Feature-flag kill-switch: fail-open-observed → enforce.** The tri-state mode is the kill-switch. Default `observe` = check + emit `deny_observed` + **allow** (the only fail-open window, time-boxed and tracked). `enforce` = fail-closed (GA steady state). Reverting any `(service,tenant)` to `observe` restores allow-all within the Redis TTL, no redeploy. The `observe→enforce` gate requires `deny_observed`==0 over a soak **longer than the max token lifetime**, so no stale-token holder crosses the flip and 403s. The fail-open path and the decorator-absence opt-in are **deleted** at GA (Phase 4) under a dated CI invariant (`rbac-no-observe-in-prod.spec.ts`) — a time-boxed shim removed per the tracked finding, not a permanent compat layer.

**Token re-mint before each flip.** In-flight pre-backfill tokens carry `resourcePermissions: []`. After backfill, epoch-keyed blobs are invalidated and a global refresh/rotation forces every live session to re-mint with populated claims **before** the flip — avoiding a compat-shim fallback in the guard (which CLAUDE.md bans).

**Same claim key = superset semantics.** The rollout does not change the token shape; it enriches the value under the existing key (unless the S3 rename is ratified, in which case guard + assertion + mobile + gateway `JwtPayload` change atomically with an invariant banning the old key). Old subgraphs ignore the additive assertion fields; new subgraphs fall back to the JWT claim — mixed-version deploys are safe.

## Cross-cutting concerns

**Security / audit.** Every RBAC definition mutation (role create/update/delete/set-default/seed) and every assignment/override change writes an immutable, tenant-scoped, PII-safe audit row whose write is atomic with (and gates) the mutation — an un-audited RBAC change becomes impossible by construction (invariant + injected `AuditLogService` + SERIALIZABLE queryRunner). Audit payloads capture permission-set diffs (added/removed `resource:action`), are ID-keyed (`userId`, never raw `targetEmail`), and mask PII via the central `maskPii()`/`logSafeUserId()` helpers. `auth.audit_logs` gains dual-identity columns (`actorHomeTenantId`/`actedOnTenantId`/`relatedAuditIds`) for impersonation linkage.

**GDPR (Article 17).** auth-service joins the tenant-erasure roster (count 10→11, atomic SSoT bump across registry + proof-ledger + invariant + module wiring). Erasure DELETEs the tenant's `tenant_roles`/`tenant_role_permissions`/`user_role_assignments` rows and **anonymizes** (hashes `userId`, strips email) RBAC rows in `auth.audit_logs` — the compliance trail survives without identifying the data subject, mirroring the farm-service pattern.

**Tenant isolation.** App-level `WHERE tr."tenantId" = $x` predicates are retained as defense-in-depth beneath **database RLS** on the `auth.*` RBAC tables (enabled once denormalized `tenant_id` columns exist). A static invariant asserts every raw SQL touching the three tables carries a tenant predicate. The gateway→subgraph HMAC binds `tenantId` into the signature so a compromised intermediary cannot swap tenants in flight.

**Two-person integrity (maker-checker).** Granting a sensitive permission/role (admin-category: role management, `users:edit_permissions`, `users:deactivate`, `settings:edit`, or `is_default`) records a PENDING row in `auth.rbac_change_approvals`; activation requires a second distinct TENANT_ADMIN approval, enforced structurally by `CHECK(approver_id <> requester_id)` + a partial unique index. Pending grants **do not enter the JWT** until approved. Feature-flagged per tenant (default OFF, requires ≥2 admins) with an audited SUPER_ADMIN break-glass for single-admin tenants.

**Impersonation.** The SUPER_ADMIN/TENANT_ADMIN blanket bypass in `TenantPermissionGuard` is **suppressed inside an impersonation context**; the effective set becomes `intersection(impersonation ceiling, impersonated user's tenant permissions)` (least-privilege). An impersonator never silently inherits tenant custom permissions; RBAC mutations under impersonation require an explicit impersonation capability (`canManageUsers`/`canAccessSettings`) and every such audit row carries both operator and target identities linked to the session. An explicit `ImpersonationContext` is propagated onto `req.user` so the guard can read it.

**Billing-tier vs permission precedence.** `Plan ⊇ Module ⊇ Permission`: a granted permission is bounded above by the plan entitlement and module assignment. Each catalogue permission declares optional `requiresEntitlement` (`PlanLimits` key) and `requiresModule`. Plan ceilings are enforced both at grant-time (UX: "upgrade to grant") and request-time (authoritative). Quota *counts* are read live from the DB; only the ceiling is claim-derived. TRIAL reads its actual (generous) catalog row for capability gates but ranks at FREE for `planMeetsMinimum` checks.

**Module-flag AND-semantics.** `@RequireModule('<code>')` + `ModuleAccessGuard` require `tenant_modules.isEnabled && !expired` for **everyone** (even TENANT_ADMIN cannot touch an unpurchased module) and `user_module_assignments.isActive` additionally for non-admins. Module ∧ permission is enforced at the subgraph boundary from the HMAC-bound `modules` claim (no hot-path auth round-trip).

**NATS / WS authz.** Event-bus authorization is **publish-time / transport-only** — subject ACLs per mTLS cert CN are the sole event-layer authz. An invariant forbids any consumer branching an authorization decision on an event-carried `role`/`performedBy` (provenance/audit only). **Commands** that trigger privileged RBAC/provisioning mutations (`SETUP_TENANT_ROLES`, cross-service user/module provisioning) get explicit command-issuer authorization — a service cert grants transport, not the right to seed/assign roles for a tenant. SCADA WebSocket handlers gate on catalogue permissions (`sensor:scada:tag-write`, `sensor:scada:alarm-ack`) resolved from the same `resourcePermissions` via a shared `WsPermissionContext`, with RS256 verification (the HS256 default is deleted); `HmiRole` becomes a FE-display projection.

**Rate limiting.** The gateway `tenant` tier limit is resolved per-request from `PLAN_CATALOG.apiRateLimit` via the `planLevel` claim (giving `apiRateLimit` its first runtime consumer) instead of a fixed 1000; `-1` = unlimited/skip. FREE/STARTER ship behind the same detect→enforce flag with a per-tenant override. Optional per-permission sub-buckets layer additively later.

**Revocation latency.** Steady-state lag is bounded by the durable `auth.users.authz_version` + Redis not-before (seconds, typical) with a ≤15m access-token TTL hard ceiling (fail-safe if Redis is down). The epoch-keyed mint blob means any token minted after a version bump commits already carries fresh perms. Offline mobile grants are advisory (server enforcement is authoritative); a server-issued permission version hard-invalidates the offline cache on the next successful fetch.

**Site-scoping (fourth axis).** `assignedSiteIds` (already in the HMAC assertion) AND-composes with fine-grained permissions: a user with `farm:tank:view` scoped to assigned sites sees only those sites. The outer-ring composition is extended from 3 gates to 4 (plan/module/permission/site) so site scope is never silently dropped.

**Sensitive GraphQL field authz.** An inventory of fields needing field-level gating independent of the parent operation (hr `payroll`, ai `cost`, messaging PII) is maintained; `@RequirePermission` on `@ResolveField` gates them so a permitted parent query cannot leak a sensitive field.

**Post-GA denial alerting/SLO.** Distinct from rollout-time `deny_observed`: a steady-state 403-spike alert (misconfiguration or attack indicator) is owned by observability with an SLO, since `deny_observed` disappears at enforce.

## Decision register

Each open decision consolidated across dimensions, with a recommendation + rationale. Contradictions surfaced by the critique are resolved here.

**D-01 — Enforcement architecture: map-driven single guard vs per-method decorator sprawl.** *Contradiction S1/S9 vs S8.* **Recommendation:** map-driven single `TenantAuthorizationGuard` consulting per-service `OPERATION_PERMISSIONS` (generalizes farm's proven `PermissionMatrixGuard`), with an optional inline `@RequirePermission` override for exceptions, and S8's `PermissionCoverageGuard` folded in as the fail-closed default. *Rationale:* highest tier (automatic + fail-closed detectable), one reviewable authz file per service, avoids ~800 edits and their drift risk. Ratify before any guard code lands.

**D-02 — Permission string format.** *Contradiction S2 vs S1/S3/S4/S7/S8.* **Recommendation:** 3-segment `domain:resource:action`. *Rationale:* domain-qualification makes cross-service collisions a compile/regex impossibility (tier-1) and matches the bounded-context model; the alias window makes migration lockout-free. Decide in Phase 0a, pin with a regex invariant, before any map is authored.

**D-03 — Catalogue home.** *Contradiction S2 vs S4/S8 vs S9-open.* **Recommendation:** new `@platform/authz-contracts` (mirroring `@platform/event-contracts`), re-exported by `backend-common` and per-service maps. *Rationale:* FE-importable by `web/shared-ui` and aquamobil without pulling `backend-common`; matches a precedent the codebase already trusts.

**D-04 — `@Roles` on tenant-data ops: delete or keep as floor.** *Contradiction S1 vs S8/S9/S12.* **Recommendation:** **keep** `@Roles` as a coarse defense-in-depth floor; do not delete. Add a lint forbidding *new* tenant-data endpoints relying on `@Roles` alone. *Rationale:* ripping out 815 decorators multiplies risk; a fine layer tightening a role floor is safe and auditable; S1 must only demote, not delete.

**D-05 — Claim name.** *Contradiction S3 vs S1/S7/S8/S11/S12.* **Recommendation:** either keep `resourcePermissions`, or rename to `effectivePermissions` **atomically** across guard + assertion + mobile + gateway `JwtPayload` in one PR pinned by an invariant banning the old key. *Rationale:* the value is genuinely effective; a misleading name is the drift the rules forbid, but a unilateral rename fractures 5 consumers. Default to rename-atomically if the coordination cost is accepted; otherwise document that `resourcePermissions` now means effective.

**D-06 — Rollout mechanism.** *Contradiction S1 (boolean env) vs S12 (tri-state config) vs S8 (env log-only).* **Recommendation:** S12's tri-state `off|observe|enforce` hot config-service mode owns the mechanism; S1 and S8 consume `RbacEnforcementModeResolver`, not parallel flags. *Rationale:* one auditable, hot, per-service/per-tenant, kill-switchable primitive; avoids a runtime warn-flag that could be left on (banned "interim" pattern).

**D-07 — Admin bypass permanence.** *Contradiction S1/S3 (permanent) vs S10 (constrain/audit/suppress-under-impersonation).* **Recommendation:** keep the bypass as default but centralize it in a single `isTenantSuperuser(user)` predicate that emits an audit event and is suppressed inside impersonation; make constraining it later a one-edit change. *Rationale:* locking a tenant admin out of their own tenant is a footgun; centralization makes the future policy change safe and traceable.

**D-08 — `mobileFeatures` claim retirement vs assertion carriage.** *Contradiction S7 vs S11/S8.* **Recommendation:** sequence S7's `mobileFeatures` retirement **after** the 24 `@RequiresMobileFeature` sites migrate to `resource:action` gating; S11 drops it from the assertion in the same GA step. *Rationale:* deleting the claim while consumers remain strands 24 enforcement sites and the assertion field.

**D-09 — ADR numbering.** *Contradiction S2/S6/S11 all claim 037.* **Recommendation:** 037 taxonomy, 038 enforcement/composition, 039 platform-tenant boundary. *Rationale:* avoids the historical collision CLAUDE.md warns about; allocate up front.

**D-10 — Single-role-per-user + overrides vs multi-role.** **Recommendation:** keep single-role + per-user overrides (the DB already enforces `unique(user_id)`; token JOIN and reconciliation assume one active role; overrides express "role plus/minus"). *Rationale:* multi-role is a cross-cutting schema + token-aggregation change with no concrete requirement yet.

**D-11 — Permission granularity.** **Recommendation:** per-resource coarse actions (view/create/edit/delete + named capabilities transfer/split/merge/plan/record/approve/emergency-stop where genuinely distinct), ~150–250 ids, not ~900 per-operation ids. *Rationale:* keeps the tenant-admin checkbox UI usable and the catalogue reviewable.

**D-12 — Deletes/tenant-lifecycle: grantable vs coarse.** **Recommendation:** domain `resource:delete` becomes grantable (the point of tenant-managed RBAC — delegate delete to a senior role); tenant-lifecycle/GDPR ops (`initiateTenantErasure`, `exportTenantData`) stay coarse `@Roles(TENANT_ADMIN)` in `PLATFORM_ROLE_OPERATIONS`.

**D-13 — Store concrete expanded ids vs wildcards.** **Recommendation:** store concrete (expand on write via the single `expandPermissions()`); wildcards are authoring sugar only. *Rationale:* keeps the guard a pure set-membership check and makes stored grants self-describing for audit.

**D-14 — Merge precedence.** **Recommendation:** revoke-wins (deny-precedence); delete the divergent grant-wins `calculateEffectivePermissions`. *Rationale:* security-safe default; matches the entity's `computeEffectivePermissions`.

**D-15 — Read-only billing in the catalogue.** **Recommendation:** include `billing:subscription:view` + `billing:invoice:view` so tenants can build a finance-viewer role; all write/billing-management stays TENANT_ADMIN-only (no catalogue id).

**D-16 — Revocation transport.** **Recommendation:** reuse the iat-based per-user not-before (`isValidToken`/`user_blacklist:<userId>`) rather than a new `pv` claim. *Rationale:* no new claim, fixes the latent unused-`isValidToken` gap, and the second-granularity race is neutralized by the epoch-keyed mint blob.

**D-17 — Claim-size strategy.** **Recommendation:** inline within a byte budget + gateway-resolved epoch-keyed reference fallback. *Rationale:* common case fully self-contained; reuses the blob already needed for mint cache + revocation; localizes indirection to the gateway. Bitmap rejected (couples token to a versioned catalogue and can't carry off-catalogue grants).

**D-18 — RoleManagementPage: delete or repurpose.** **Recommendation:** repurpose into a platform RBAC console (catalogue view + system-role-template CRUD + cross-tenant adoption/drift observability). *Rationale:* the platform genuinely needs template management + observability; the surface already sits at the correct SUPER_ADMIN tier; deleting discards a needed capability.

**D-19 — SUPER_ADMIN on tenant-role WRITE grants.** **Recommendation:** remove `Role.SUPER_ADMIN` from the tenant-role write mutations (TENANT_ADMIN-only; SUPER_ADMIN acts in-tenant only via impersonation). *Rationale:* `tenantId` is JWT-sourced so SUPER_ADMIN can only ever hit its own tenant anyway; listing it is misleading and makes the boundary a tier-1 structural fact.

**D-20 — System role templates location + propagation.** **Recommendation:** `admin.system_role_templates` table (runtime-editable, versioned, audited); **no** auto-propagation to existing tenants (tenants own their diverged roles; the observability tab surfaces drift; `seedTenantRoles` gives an opt-in reset).

**D-21 — Two-person single-admin tenant policy.** **Recommendation:** default maker-checker OFF, require ≥2 distinct TENANT_ADMINs to enable; audited SUPER_ADMIN break-glass as second approver for single-admin tenants (break-glass itself two-person-logged).

**D-22 — RBAC audit home.** **Recommendation:** add dual-identity columns to `auth.audit_logs` and single-write there (atomic fail-closed with the tx); additionally emit to `shared.audit_logs` ONLY for impersonation-context RBAC changes.

**D-23 — Erasure: delete vs anonymize RBAC data.** **Recommendation:** DELETE the three RBAC tables' rows for the tenant; ANONYMIZE (hash userId, strip email) the `auth.audit_logs` RBAC rows.

**D-24 — Impersonation effective set.** **Recommendation:** intersection of the impersonation ceiling AND the impersonated user's tenant permissions (least-privilege).

**D-25 — Live path: raw SQL vs ORM.** **Recommendation:** keep raw SQL for tenant-scoping (deliberate tenant-ownership laundering via `tenant_roles` joins), entities as the drift-test SSoT only.

**D-26 — Plan ceiling enforcement point.** **Recommendation:** both grant-time (UX, prevents dangling grants) and request-time (authoritative, plan can downgrade after a grant); the descriptor powers both.

**D-27 — Module gate on TENANT_ADMIN.** **Recommendation:** `tenant_modules` gate binds everyone (a tenant-purchase fact); `user_module_assignments` gate exempts admins (intra-tenant delegation).

**D-28 — Rate-limit granularity.** **Recommendation:** plan-tier tenant limit now (wire `apiRateLimit`); defer per-permission sub-buckets until a concrete abuse case.

**D-29 — Assertion carries planLevel only vs full entitlement bitset.** **Recommendation:** ship only `planLevel`; subgraphs resolve booleans from the frozen `PLAN_CATALOG` (free resolution, no second representation to drift).

**D-30 — TRIAL treatment.** **Recommendation:** capability/quota gates read the actual (generous) TRIAL catalog row; paid-tier minimum gates use `PLAN_LEVEL` (TRIAL ranks FREE) so TRIAL never satisfies a "PROFESSIONAL-or-higher" check. Document the precedence in the ADR.

**D-31 — Mobile admin full-access representation.** **Recommendation:** `*` wildcard element in `effectivePermissions`, `hasPermission` short-circuits. *Rationale:* keeps the client entirely role-free; avoids shipping the whole catalogue per identity response.

**D-32 — Mobile reads JWT claim vs identity query.** **Recommendation:** identity query result (the JWT claim omits the key when empty and is `[]` for admins; client-side JWT decoding is brittle). Both derive from one server resolver so they can't diverge.

**D-33 — Denominator definition.** **Recommendation:** all non-`@Public`, non-`@SkipTenantGuard` resolver+route handlers in the 7 `rbacEnforcementTarget` services. *Rationale:* reads touch tenant data too; least-gameable definition of "no tenant-data handler is unguarded."

**D-34 — GA fail-open removal guarantee.** **Recommendation:** dated CI invariant `rbac-no-observe-in-prod.spec.ts` + compiled default flipped to enforce + a CRITICAL tracked finding (owner+deadline+ID). *Rationale:* machine-gated removal satisfies the no-permanent-shim rule.

**D-35 — `auth.users.role` column fate.** *Critique missing-item.* **Recommendation:** make it a derived/read-only display projection of the authoritative tenant assignment; repoint legacy write paths; a reconciliation invariant asserts it matches the assignment's system-role tier. *Rationale:* eliminates the dual source-of-truth divergence.

## Definition of Done

The program is complete when **all** of the following hold and are machine-checked:

**(a) Endpoint burn-down to 100%.** The adoption ratchet `BASELINE_RATIO[service] == 1.0` for all 7 tenant-scoped services; every non-`@Public`, non-`@SkipTenantGuard` tenant-data GraphQL operation and REST route carries a catalogue-valid fine-grained permission (via the map or an inline decorator). The runtime `rbac_enforced_endpoint_ratio{service}` gauge reads 1.0 per service. Burn-down: **0.53% → 100%** (5 → ~944 endpoints).

**(b) Zero orphan permissions.** Every `@RequirePermission`/`@RequireTenantPermission` argument, every seeded `resource_permissions` string, and every `OPERATION_PERMISSIONS` value ∈ the `@platform/authz-contracts` catalogue (the `edge:manage-io-config` class is impossible — compile error + membership invariant).

**(c) Guard live + fail-closed by default.** `TenantAuthorizationGuard` runs as `APP_GUARD` in `enforce` by default in all 7 services; the decorator-absence pass-through is removed for tenant-scoped services (`PermissionCoverageGuard` fail-closes any unmapped tenant-data mutation). A guard-registration invariant asserts this.

**(d) No fail-open in prod.** `observe`/`off` forbidden in production config by the dated `rbac-no-observe-in-prod.spec.ts` invariant; the compiled default is `enforce`.

**(e) One model, dead surfaces gone.** `shared.user_permissions`, the orphaned admin-api `tenant-role.service.ts`, `RoleTemplateService` static templates + `tenant_custom_roles` path, the dead gateway `PermissionGuard` stack, dead OPA authz scaffolding, and the `mobileFeatures` claim (post-consumer-migration) are deleted; exactly one catalogue literal exists (grep-guard).

**(f) Mobile on the claim.** aquamobil resolves authz exclusively from `effectivePermissions` (invariant: no `role-rank`/`meetsRoleFloor`/`getMyMobileSettings` in authz paths; identity document selects `effectivePermissions`/`mobileAccessEnabled`).

**(g) Effective, propagated, revocable.** The token carries the override-applied, expiry-aware effective set; it reaches subgraphs through the HMAC assertion (golden round-trip invariant); revocation is bounded to seconds via `authz_version`; token effective-projection has a TDD unit lock.

**(h) Cross-cutting closed.** RBAC-mutation audit coverage invariant green; auth-service in the GDPR erasure roster (count 11); RLS on the `auth.*` RBAC tables; two-person for sensitive grants; impersonation bypass suppression; billing/module/site outer-ring composition enforced.

**(i) Soak clean.** A 30-day post-GA window with `deny_observed`==0 and no rollback events; runbook + Grafana burn-down dashboard published.

**The invariant that makes regression impossible:** the adoption ratchet is **monotonic** — `BASELINE_RATIO` may only rise, and at GA it is pinned to 1.0. Combined with (c) the removed pass-through (an un-annotated tenant-data handler hard-denies) and (b) the compile-time `PermissionId` union + catalogue-membership invariant, it is **structurally impossible** to merge a new tenant-data endpoint without a catalogue-valid fine-grained permission, or to reintroduce a second permission vocabulary, or to ship a `@RequireTenantPermission` in a service without a consuming guard. Coverage cannot regress below 100%; the fixed-enum model cannot reclaim a tenant-data endpoint.
