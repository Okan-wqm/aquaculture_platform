# PR #1423 — the integration's own CI failures (2026-09-05)

**Reviewer:** zcode (integration). **Scope:** the branch-triage integration head, first CI run.

The first CI run on `claude/branch-evaluation-merge-s5grgw` turned 19 checks red. Each was
root-caused against the merged tree rather than re-run; the findings below are the ones that are
defects in the integration itself, each with the fix that closes it.

## PROC-MEDIUM-022 — merged trailers name finding ids the ledger cannot carry

**Severity:** MEDIUM. **Owner:** zcode. **State:** IN-PROGRESS.

**Evidence.**

- `tools/gates/commit-msg-validator.ts` — `validate-closes` failed on 8 merged commits carrying 12
  trailers of the form `Closes: docs/reviews/edge-expert/2026-07-12-pr935-e2e-review.md#PR935-HIGH-001`.
- `docs/reviews/_registry/findings.jsonl.schema.json` — the id pattern admits a closed alternation of
  domain prefixes; `PR935` is not one and must not become one (the schema says so about `DATAMIG`).
- `docs/reviews/edge-expert/2026-07-12-pr935-e2e-review.md` — the anchors exist; the findings are
  real. The #935 integration re-registered the _audit's_ 59 findings and missed this second review
  file's 12 entirely, so the trailers pointed at nothing in the ledger.

**Rule violated.** Every fix commit's `Closes:` trailer must resolve, or `docs/reviews/` is audit
theater — and a merged trailer cannot be amended, because rewriting published history is forbidden.

**Fix (this change).**

- The 12 findings are registered where they belong: `EDGE-HIGH-029`…`EDGE-LOW-040`, citing the PR935
  review file, with the evidence and rule each one carries there.
- `docs/reviews/_registry/finding-id-aliases.yaml` maps each historical id onto its ledger id, with
  the review file, the merged commits that name it, a date and a reason.
- `tools/gates/finding-id-aliases.ts` is the single loader. The commit-msg validator admits an alias
  only when its canonical id is in the ledger; `collectMergedClosures` attaches aliases to every
  candidate, so `close`, `reconcile` and the closure-drift gate resolve a historical trailer the same
  way rather than each inventing an answer.
- `tests/invariants/finding-id-aliases.spec.ts` keeps it from becoming an exemption list: an alias
  must resolve to a real row, must not shadow one, must be unique, must carry its audit evidence, and
  its commits must exist. It earned its keep immediately — it caught `6e680743` being parsed as
  scientific notation (`Infinity`) by unquoted YAML.

**Second round.** Registering the rows was not the whole fix: `three-store-invariants` then failed
because `docs/reviews/edge-expert/2026-07-12-pr935-e2e-review.md` cited only the `PR935-*` ids, and a
ledger row must be findable in the document it names. The review file now carries a **Ledger ids**
table mapping each review id to its ledger id, so a reader arriving from either direction — a merged
trailer or a `findings.jsonl` row — lands on the same finding. The ids stay in the table rather than
in the headings because the headings are the anchors the merged trailers point at.

**Closure criterion.** `validate-closes` passes on the PR range; `three-store-invariants` and
`finding-id-aliases` pass; a trailer with neither a ledger row nor an alias still fails the gate.

## ALERT-HIGH-002 — the sensor-reading handler overrode the delivery-class SSoT

**Severity:** HIGH. **Owner:** zcode. **State:** IN-PROGRESS.

**Evidence.**

- `apps/alert-engine/src/alert/event-handlers/sensor-reading.handler.ts` caught and rethrew
  unconditionally, with a comment arguing a threshold crossing is one-shot even when the reading
  stream is not (PR #1338 Task 1.5).
- `libs/event-contracts/src/event-delivery-semantics.ts` classifies `SensorReading: 'reproducible'`
  and its comment addresses that exact argument: "the next reading for the same sensor arrives within
  seconds and re-evaluates every threshold rule. Rethrowing here would turn one bad reading into a
  redelivery storm on the platform's highest-volume subject for no gain."
- `tests/invariants/feeding-event-delivery-semantics.spec.ts` failed: the handler catches without
  consulting `requiresDurableDelivery`.

**Rule violated.** One authority decides delivery semantics. A handler that hard-codes its own answer
makes the classification advisory.

**Fix.** The handler defers to `requiresDurableDelivery(event.eventType)` like every sibling; the two
specs that pinned the unconditional rethrow now pin the classification-driven contract, and a third
covers the durable branch. Both merges' intents survive: nothing is swallowed for a one-shot event,
and a reproducible one is not redelivered.

## INFRA-MEDIUM-145 — a migration ran two statements in one query and read the wrong result

**Severity:** MEDIUM. **Owner:** zcode. **State:** IN-PROGRESS.

**Evidence.** `apps/config-service/src/database/migrations/1807400000000-RestoreConfigSchemaOwnerBoundary.ts`
sent a `DO $$ … $$;` block and a `SELECT … AS applied` as ONE query string. In a multi-statement
simple query the driver returns one result per statement and TypeORM hands back the last one's
`rows`, which for the DO block is absent — so `rows[0]` threw `Cannot read properties of undefined`,
aborting the config chain and with it all 71 `bootstrap-from-scratch` assertions, plus
`schema-invariants` and `tenant-clone-parity`.

**Rule violated.** One statement per `query()` call: a migration must read the result it asked for.

**Fix.** The DO block and the SELECT are separate calls. No other migration in the tree pairs a DO
block with a trailing SELECT in one string.

## MSG-HIGH-079 — two messaging admin RPC handlers had no subscribe grant

**Severity:** HIGH. **Owner:** messaging-expert. **State:** IN-PROGRESS.

**Evidence.** `e2e/tests/integration/nats-invariants.spec.ts` reported RPC grant drift:
`request.messaging.admin.getMonitoringStats` and `request.messaging.admin.getTenantsOverview` are
handled by `apps/messaging-service` but appear in no `subscribe` list in
`infrastructure/nats/services.yaml`. A handler without a subscribe grant never receives the request,
and the admin caller without the matching publish grant times out — the two surfaces the PR #962
re-derivation replaced the old 501 stubs with would have been dead in production.

**Rule violated.** ADR-015: `services.yaml` is the SSoT; every handled pattern carries a subscribe
grant and every sent subject a publish grant, in the same commit as the handler.

**Fix.** Both subjects added to the admin caller's `publish` list and the messaging service's
`subscribe` list; `infrastructure/docker/nats/nats.conf` regenerated by
`scripts/nats/generate-nats-conf.py` (never hand-edited). `nats-invariants` passes 110/110 and
`--check` reports no drift.

## EDGE-HIGH-041 — the Rust unit tests derive their SQLCipher key through `/etc/suderra`

**Severity:** HIGH. **Owner:** edge-expert. **State:** IN-PROGRESS.

**Evidence.** `compile + test-compile gate` and both `cargo test --all-targets` jobs failed with four
`db::sqlcipher_factory` tests panicking on `Failed to create secret-key parent directory
/etc/suderra: Permission denied (os error 13)`. `open_device_secret` derives the v1 key through
`db_secret::read_or_create_v1_secret`, whose default path is the production `/etc/suderra/db.key`.
The crate had a sandbox — `offline_queue::test_support::ensure_key_sandbox` — but it was OPT-IN, and
these four tests never opted in. That is invisible to an author working as root (the directory gets
created) and fatal on an unprivileged CI runner, which is why the suite passed locally at 2161 tests
and failed in CI on the same commit.

**Rule violated.** A unit test must not depend on write access to a production system path — and
hermeticity that depends on each author remembering an opt-in is not hermeticity.

**Fix.** `db_secret::secret_key_path()` is now the single resolver for "where the v1 secret lives":
the `SUDERRA_DB_KEY_PATH` override when set, else the build's default — `/etc/suderra/db.key` in a
production build, a per-process temp sandbox under `#[cfg(test)]`. The opt-in is gone: no in-crate
test can reach `/etc` through this path whether or not its author asked. `ensure_key_sandbox` keeps
the one job a default cannot do (seeding deterministic bytes) and delegates the path to that owner;
`db_migration::cli_runtime::read_secret_key_for_migration` drops its copy of the env-override,
default path and minimum-length literals and reads the same resolver, keeping its read-only
fail-closed semantics.

**Closure criterion.** With `/etc/suderra` absent, `cargo test --locked --all-targets --no-fail-fast
-- --test-threads=1` passes (2163 tests, both feature sets) and does not recreate the directory —
verified locally by deleting it first. Two tests pin the resolver: the test-build default resolves
inside the temp dir, and the env override still wins.

## INFRA-MEDIUM-146 — `tools/scripts` was linted under a project that cannot resolve its imports

**Severity:** MEDIUM. **Owner:** infra-expert. **State:** IN-PROGRESS.

**Evidence.** `lint-changed-files.sh` reported `no-unsafe-assignment` / `no-unsafe-call` /
`no-unsafe-member-access` on `tools/scripts/telemetry-dlq-replay.ts`, describing `connect()`'s result
as "an error typed value". The code is correctly typed: `tsc -p tools/scripts/tsconfig.json` is
clean. The lint parser was using `tsconfig.base.json` (`moduleResolution: "node"`) because
`TS_PROJECTS` has no entry for `tools/scripts`, and `@nats-io/nats-core` publishes `"types":
"./lib/mod.d.js"` — a `.js` path — so node10 resolution fails and every value derived from it becomes
an error type.

**Rule violated.** A directory's lint program must be the TS project that owns it. A parser pinned to
a config that cannot resolve the code's imports invents type errors, and the fix an author would
reach for is a suppression on correct code.

**Fix.** `tools/scripts/tsconfig.eslint.json` extends the directory's own tsconfig (Bundler
resolution) and `tools/scripts` joins `NON_PROVENANCE_TS_PROJECTS` — the mechanism the config already
documents for exactly this. Verified that the other files in the directory report the same findings
before and after the pin, so nothing else changed.

## PROC-MEDIUM-023 — the merged branches brought 56 new error-level lint findings

**Severity:** MEDIUM. **Owner:** zcode. **State:** IN-PROGRESS.

**Evidence.** `lint-changed-files.sh` reported 56 error-level findings new relative to `origin/main`
across ten files, all of them code this integration merged: `require-await` on hooks that never
await, `no-unsafe-*` on `jest.fn()` doubles whose recorded calls the assertions read back as `any`,
`await` on a synchronous consume callback, non-null assertions, `import/order`, a root-barrel import,
a dead `const`, and eleven `console.*` calls in an operator CLI.

**Rule violated.** An integration merges the branch's defects too: code entering main passes the same
gate as code written on main.

**Fix.** Each one at its cause, not its symptom. The Apollo hooks return their promise instead of
being `async` for a contract they never use; `mgetScoped` carries each key's target position so the
split fetch never re-indexes its input; the two NATS spec doubles are typed FROM `StreamAPI['add']`
and `ConsumerAPI['add']`, so `mock.calls` is checked against what the bus really passes; the DLQ spec
stops awaiting a `void` callback and keeps the macrotask flush that actually advances it; the
predicates that never await return `Promise.resolve`/`reject`; the CLI writes through
`process.stdout`/`stderr` like its lint-clean sibling `emit-subgraph-sdl.ts`; the barrel import moves
to `@aquaculture/backend-common/event-dedup`. Nothing is suppressed and no rule is relaxed.

**Not fixed here (and why).** The same run reports five `@nx/enforce-module-boundaries` errors for a
`backend-common` <-> `event-bus` project cycle. The cycle exists on `main` — `nats-event-bus.ts`
imports `backend-common/nats` there and `security-event.service.ts` imports `@platform/event-bus` —
and surfaces at the new import LINES rather than being introduced by them. CI does not report them
(its 56 findings carry none). Breaking that cycle is a library-boundary refactor with no relation to
this integration, so it is recorded here rather than attempted inside a merge PR.

## FARM-HIGH-316 — the Postgres e2e harness mirrors production wiring by hand, and it drifted

**Severity:** HIGH. **Owner:** farm-expert. **State:** IN-PROGRESS.

**Evidence.** `farm-service:test:integration` failed on
`feeding-record-tenant-isolation.postgres.spec.ts` with `EntityMetadataNotFoundError: No metadata for
"FeedingDayPlan"`, thrown from `create-feeding-record.handler.ts:160` — the PR #1031 feeding-protocol
merge made the handler bind the unit's active day plan, and the fixture's DataSource had never heard
of that entity. Production is unaffected: `createServiceTypeOrmConfig` runs `autoLoadEntities: true`,
so every entity any module registers is in the DataSource automatically.

**Rule violated.** A harness must derive what it registers from the code under test. This one kept
TWO hand-written mirrors of production wiring — the `entities: [...]` array and a per-table
`CREATE TABLE … (LIKE "farm".x)` sequence — that must be edited in lockstep whenever a handler
reaches one more table, and whose omission shows up only at runtime, inside a handler, on a lane that
cannot run where Docker is unavailable. The file already carried a comment from the previous
occurrence of this exact class (`FinanceSettings`), and a second from the occurrence before that (a
partial double of a growing service). Three victims is a defect in the harness, not in three authors.

**Fix.** The entity set is registered from what the code under test actually touches — `FeedingDayPlan`
plus `FeedingMeal`, `FeedingProtocolV2` and `ProtocolAssignment`, which the REAL `DayPlanRecalcService`
the fixture wires reads while recalculating (derived by reading every `manager.<op>(Entity)` call in
the handler and in each collaborator the spec constructs, not by adding the one name the error
printed). And the second mirror is deleted: `createTenantSchema` now clones every per-tenant table
`synchronize` actually created in `farm`, read back from `information_schema`, skipping the tables
whose entity declares an explicit `schema:` (cross-tenant by ADR-011 — the outbox). Registering an
entity is now the single edit; the tenant schema follows.

**Second round, and the reason there was one.** The entity fix was pushed without running the lane
— "no Docker here" — and CI then surfaced the next assertion down: `feedTypeDistribution` carries a
per-feed `cost` the expectation omitted, harmlessly, because that line had never been reachable. The
handler is byte-identical to `main` and `feeding-summary-response-contract.spec` pins the field, so
the expectation was completed (`cost: 25`, equal to the `totalFeedCost` asserted two lines above).
CI: the `test` job is green on `0c255f800`.

**The lane now runs without Docker.** Fixing a Postgres-lane defect blind is what produced the second
round, and the fixture's own comments record it happening before. `bootPostgresContainer` gained an
external-server mode: with `MIGRATION_HARNESS_PG_URL=postgres://user:pass@host:port/maintenance_db`
set it starts no container, creates one fresh database per boot, drops it on `shutdownHarness`, and
— because roles are cluster-global where a container's never were — snapshots `pg_roles` at boot and
drops the roles the boot added. A suite cannot tell the two modes apart and needs no change; a set
but unusable URL throws rather than silently falling back to Docker (unit-pinned). With it the full
farm-service integration lane was run here against a local Postgres 16, with
`feeding-record-tenant-isolation` passing on both fixes — before, not after, pushing.

## SUPPLY-MEDIUM-008 — security-audit is red on an advisory with no non-breaking remediation

**Severity:** MEDIUM. **Owner:** supply-chain-auditor. **State:** OPEN → closed by the storage client
swap below. **Deadline:** 2026-10-03.

**Evidence.** `npm audit --omit=dev` reports GHSA-528h-pc64-c93x on `stream-json <= 3.4.0`, installed
at 1.9.1 as a transitive dependency of `minio@8.0.7`. Both are at byte-identical versions on `main`,
whose last `ci-affected` run passed at 06:46 today: `npm audit` queries the advisory database at run
time, so the same lockfile turned red with no code change on either branch.

**Why it cannot be fixed here — checked, not assumed.**

- The fixed line is `stream-json` 3.5.0/3.6.0. That package is ESM-only (`"type": "module"`) and
  restructured under `src/`, with an `exports` map. `minio/dist/main/notification.js` does
  `require('stream-json/jsonl/Parser.js')`, and against 3.6.0 that resolution fails outright:
  `MODULE_NOT_FOUND ... /stream-json/src/jsonl/Parser.js` (verified in a scratch install).
- That require is not lazy. `minio`'s package main, `dist/main/minio.js`, requires `./notification.js`
  eagerly, as does `internal/client.js` — so an `overrides` entry to the fixed line would break
  `require('minio')` for every storage path in the platform, not just the notification API.
- `minio@8.0.7` is the newest published `minio`; there is no upstream release carrying a fixed range.
- npm's own `fixAvailable` is a **downgrade** to `minio@7.1.3`, flagged `isSemVerMajor`.
- The gate has no allowlist to reach for: `security-audit` runs raw `npm audit` across six surfaces
  with no ignore file, by design.

**Fix — the client is replaced, not the advisory ignored.** The `security-audit` check is required by
`merge-gate`, so "tracked" was never going to get this PR onto `main`; and the same red would meet
every later PR, since `main` carries the identical tree. `minio` was used from exactly one file,
`libs/storage/src/minio-client.service.ts`, through eleven calls that map one-to-one onto S3
commands, and `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner` were already dependencies
(messaging-service's media path, with `forcePathStyle: true` for MinIO). The service now speaks S3
through the AWS SDK: same class name (it is still the client of the MinIO server, and every consumer
imports it by that name), same public methods and signatures, same result shapes. The contract details
the swap had to keep are pinned by a new unit spec (42 storage tests green): bare unquoted ETags,
bare lowercase user metadata, and the internal URL shape. One documented promise the old code never
kept is now real — `getPresignedUploadUrl` computed a `Content-Type` condition and then never passed
it; the SDK signs it, so a browser must upload with the declared type. `minio` is uninstalled;
`stream-json` leaves the tree with it.

**Verification.** `npm audit --audit-level=moderate --omit=dev` → 0 vulnerabilities;
`npm audit --audit-level=high` (full tree) → exit 0; the dependency-graph contract step and both
standalone lockfiles unaffected; the four consumers' specs green (farm incident-media and orphan
cleanup, admin reports, sensor parquet codec).

**Trailer correction.** The commit that registered this finding (`7f925210a`) carried a `Closes:`
trailer, which is wrong — registering an advisory is not removing it, and the closure derivation
would have marked the row RESOLVED at the next `reconcile`. The trailer cannot be amended under the
force-push ban, so `7f925210a` is recorded in this finding's `rejected_closing_commits` through the
override reopen built for exactly this case (PROC-MEDIUM-021). Neither the ceremony nor the
derivation may count it again; only a NEW commit that actually removes the vulnerable range closes
SUPPLY-MEDIUM-008.

## Not this PR's failure

None left standing. `security-audit` was, until the storage client swap under SUPPLY-MEDIUM-008 made
the tree clean; it would have failed identically on `main`'s tree, and now closes here.
