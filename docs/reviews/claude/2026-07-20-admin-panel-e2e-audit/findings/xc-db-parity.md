### APA-376 [HIGH] Auth-schema RBAC + invitation DDL is owned by admin-api's migration chain (ownership inversion, deploy-order coupling)

- **Status:** CONFIRMED+DESIGNED
- **Symptom:** admin-api's migration 1800200000000-CreateAdminEntitySurfaceTables creates four tables in the auth schema: auth.tenant_roles, auth.tenant_role_permissions, auth.user_role_assignments, auth.tenant_invitations. auth-service's LIVE migration chain (apps/auth-service/src/migrations/*.ts) contains zero DDL for these tables (only the retired .archive chain did), yet auth-service maps them with runtime entities (tenant-role.entity.ts, tenant-role-permission.entity.ts, user-role-assignment.entity.ts) and serves the RBAC SSoT from them. admin-api's chain also adds an index on the auth table (1801100000000) and backfills auth-schema DATA (1801300000000-BackfillMessagingAiRoleCapabilities). Consequence: any environment that runs only auth-service migrations (standalone auth deploy, auth integration-test DB) has entities without tables — auth-service's boot-time SchemaDriftValidator will fail until admin-api's migrations run first. The auth entity docblock (RBAC-HIGH-011) acknowledges 'DDL was owned by admin-api migrations' and added entities for drift visibility, but the DDL ownership itself was never moved to the owning service, violating the per-service migration-ownership pattern (ADR-011/012). Known hardening gaps on these tables (missing FK tenantId->auth.tenants, no unique on (tenantId, LOWER(name)), single-default invariant app-only) are tracked as RBAC-MEDIUM-012/013 in the same docblock.
- **Evidence:**
  - `/home/user/aquaculture_platform/apps/admin-api-service/src/migrations/1800200000000-CreateAdminEntitySurfaceTables.ts:10 (CREATE TABLE auth.tenant_roles), :56 (auth.tenant_role_permissions), :69 (auth.user_role_assignments), :98 (auth.tenant_invitations)`
  - `/home/user/aquaculture_platform/apps/admin-api-service/src/migrations/1801100000000-AddTenantRolePermissionsRoleIdIndex.ts (admin chain indexing an auth-schema table)`
  - `/home/user/aquaculture_platform/apps/admin-api-service/src/migrations/1801300000000-BackfillMessagingAiRoleCapabilities.ts (admin chain mutating auth.tenant_role_permissions data)`
  - `/home/user/aquaculture_platform/apps/auth-service/src/modules/tenant/entities/tenant-role.entity.ts:10-36 (docblock: 'DDL was owned by admin-api migrations'; @Entity('tenant_roles', { schema: 'auth' }))`
  - `apps/auth-service/src/migrations/ live chain grep for 'tenant_roles' returns zero matches (verified 2026-07-19)`
- **Verification:** Every cited fact verified against current code. admin-api's live chain creates four auth-schema tables (1800200000000 lines 10/56/69/98), indexes one (1801100000000), and backfills auth data (1801300000000, whose docblock admits admin-api owns the DDL). auth-service's live chain (apps/auth-service/src/migrations/[0-9]*) has zero DDL for them — only the retired .archive chain does. The failure is concretely reachable: (a) auth registers TenantRole/TenantRolePermission via TypeOrmModule.forFeature (tenant.module.ts:38-52), so they are in DataSource metadata, and SchemaDriftValidator treats a missing table as error-level drift (schema-drift-validator.service.ts:310-332) with fatal forced true in production-like envs — an auth DB migrated only by auth's own chain fails auth-service boot; (b) token minting raw-SQL JOINs all three tables on EVERY mint (token.service.ts:589-591), so a fresh dev DB crashes token minting until admin-api-service happens to run its chain (services run their own runners in parallel in dev per schema-registry docblock); (c) db-migrate's SCHEMA_REGISTRY maps schema 'auth' to only auth-service's glob and runs 'admin' LAST, so on a fresh DB auth's postMigrationHardening tenant-RLS pass runs before these tenantId-bearing tables exist — they receive no RLS in the first deploy pass (extra consequence the finding missed); (d) the DDL is recorded in the admin schema's migration ledger, so auth's ledger doesn't describe auth's schema. Not CRITICAL because the standard full-deploy topology works (admin chain always runs, IF NOT EXISTS idempotent, db-migrate completes before services boot), but HIGH stands: the trust root's boot and request hot path depend on the last-ordered platform-utility service's migration chain, violating ADR-011/012 per-service migration ownership, with the docblocks explicitly acknowledging the inversion (tier-4 documentation where tier-1/2 was possible).
- **Root cause:** The DB link of the chain broke at ownership-transfer time. The centralized RBAC + invitation tables were created when admin-api was their only writer, so the DDL landed in admin-api's migration chain. When runtime ownership of the RBAC SSoT moved into auth-service (RBAC-HIGH-011: entities added, raw-SQL reads on every token mint, seeding via tenant provisioning), the table LIFECYCLE (DDL, indexes, data backfills) was never transferred to the owning service — the remediation stopped at tier-3 'make it detectable' (entities for drift visibility) plus tier-4 docblocks stating 'DDL was owned by admin-api migrations'. Result: SCHEMA_REGISTRY's auth entry (migrationsGlob = apps/auth-service/src/migrations only) no longer describes the auth schema; auth is not self-sufficient (entities + hot-path SQL without tables in any auth-only environment); fresh-DB deploys order auth's RLS hardening before the tables exist; and nothing at build/test time prevents any service's chain from mutating a foreign schema — this is an instance of the systemic class 'migration chain owning another service's schema surface'.
- **Fix design:** Local fix (tier 2 — make correct behavior automatic): add an adoption migration to auth-service's chain, apps/auth-service/src/migrations/1807300000000-AdoptCentralizedRbacTables.ts, containing the full canonical DDL — CREATE TABLE IF NOT EXISTS + all indexes (including idx_tenant_role_permissions_role_id from admin's 1801100000000) — for auth.tenant_roles, auth.tenant_role_permissions, auth.user_role_assignments, auth.tenant_invitations, column-for-column identical to the deployed shape. IF NOT EXISTS makes it a recorded no-op on all deployed DBs (forward-only, blue-green safe; the already-applied admin migrations stay untouched — history is immutable, they simply become no-ops on fresh DBs because auth is slot 1 in SCHEMA_REGISTRY and now creates the tables first). This makes auth self-sufficient (boot drift validation and token minting work with only auth's chain applied), fixes the fresh-DB RLS ordering gap (tables now exist when auth's postMigrationHardening tenant-RLS pass runs), and puts the DDL in the auth ledger. Reference RBAC-MEDIUM-012/013 (FK tenantId->auth.tenants, UNIQUE (tenantId, LOWER(name)), partial-unique single-default) as the follow-on hardening migration now that auth owns the DDL — cite their finding IDs, do not silently fold. Pattern fix (tier 3 — make violations detectable, systemic class): new tests/invariants/migration-schema-ownership.spec.ts that, for every SCHEMA_REGISTRY entry, parses the migration files matched by its glob, extracts schema-qualified identifiers from the SQL, and asserts each chain references only its own schema (plus tenant_<uuid> interpolation and extension bootstrap in public). The already-applied admin-api migrations touching auth are pinned as an EXACT frozen set (set-equality on filenames — immutable history, not a growable allowlist; any new cross-schema statement in any chain fails CI). Add the inverse completeness assertion: every table name mapped by an auth @Entity has CREATE TABLE DDL in auth's own chain. Repoint the parity anchor: extend apps/auth-service/src/modules/tenant/entities/__tests__/centralized-rbac-entities.spec.ts to pin entity columns against the new auth-owned adoption migration (removing the implicit cross-service dependency on admin-api's migration file) and correct the three entity docblocks that state DDL is admin-owned. admin-api's TenantInvitation mapping (apps/admin-api-service/src/tenant/entities/tenant.entity.ts:247, synchronize:false) may keep reading the table, but its lifecycle contract now lives in auth; future auth-schema DML backfills (the 1801300000000 class) must land in auth's chain — enforced by the same invariant since it scans schema-qualified DML targets too.
- **Files to change:**

  - `tests/invariants/migration-schema-ownership.spec.ts`
  - `apps/auth-service/src/modules/tenant/entities/__tests__/centralized-rbac-entities.spec.ts`

- **Proof of fix:** New tests/invariants/migration-schema-ownership.spec.ts: (1) for every SCHEMA_REGISTRY entry, every migration file in its migrationsGlob references only its own schema in schema-qualified SQL (tenant_<uuid> interpolation exempt), with the historical admin-api->auth migrations pinned by exact filename set-equality so the frozen set can never grow; (2) every table mapped by an auth-service @Entity has CREATE TABLE DDL present in auth-service's own chain (self-sufficiency).
