## Key Findings

### 1. SRI + Module Federation is a native gap
Webpack's ModuleFederationPlugin does not natively emit SRI hashes for federated chunks. The canonical `webpack-subresource-integrity` plugin explicitly tracks an unresolved incompatibility (issue #176): hashes are not computed for chunks generated by the MF plugin because the federated chunk graph is extended after SRI calculation runs. This means any production MFE host that loads remotes from a CDN is, by default, trusting the CDN (and anything in the network path) to deliver unmodified JavaScript. A supply-chain compromise of a single remote collapses the whole shell.

### 2. Correct pattern: Runtime plugin + `createScript` / `beforeRequest` hook
Module Federation exposes a runtime plugin API with hooks: `beforeInit`, `beforeRequest`, `afterResolve`, `onLoad`, `errorLoadRemote`, plus a `createScript` hook that lets the host return the exact `<script>` element that will be appended to the DOM for the remote entry. The accepted pattern (confirmed by MF maintainers in Discussion #2240) is:
1. Maintain a build-time-produced manifest (`remoteIntegrity.json` or similar) mapping `remoteName -> { url, integrity: 'sha384-...' }`.
2. Register a runtime plugin that implements `createScript({ url })`: construct a `HTMLScriptElement`, set `.integrity`, `.crossOrigin = 'anonymous'`, and return it. The browser then performs the SRI check itself — no manual hash verification in JS.
3. In `beforeRequest`, reject any remote whose resolved URL is not an exact match against a static allowlist keyed by `remoteName`. This is the second layer: SRI protects content; the allowlist protects the origin.

### 3. `createElement` monkey-patch (SH-SEC-04 pattern)
The shell's current `remoteIntegrity.ts` patches `document.createElement('script')` and, when `src` is assigned, checks the URL against an allowlist. This is a legitimate defence-in-depth pattern but has two known pitfalls:
- It must be installed **before any remote code runs**, i.e. as the very first module in the shell's entry chunk. Any import that transitively touches the DOM before the patch is installed creates a bypass window.
- It must handle both property assignment (`script.src = '...'`) AND `setAttribute('src', '...')` AND constructor-style creation via `new Image()`-style tricks. Modern attackers use `Document.prototype.createElement.call(...)` or `Reflect.apply` to evade a patched global — the patch must be applied on `Document.prototype.createElement`, not just the bound instance method.
- It must not break error handling for legitimate third-party scripts (Sentry, analytics) — these need to be in the same allowlist or routed through a separate loader.

### 4. Singleton shared dependencies are a correctness AND security concern
Per the MF docs, shared dependencies must be declared with `{ singleton: true, strictVersion: true, requiredVersion: '^X.Y.Z' }` for React, ReactDOM, react-router-dom, @tanstack/react-query, and any library that holds module-scoped state (Zustand stores, i18n instances, Sentry client). Without `singleton: true`, each remote can load its own copy and:
- React: "Invalid hook call" / "two Reacts" errors; broken Suspense boundaries.
- react-router-dom: two Router contexts → navigation no-ops silently.
- @tanstack/react-query: two QueryClients → cache invalidation and MFE data isolation break unpredictably.
- Zustand: each remote gets its own store instance → cross-MFE state desync (and, for auth state, potentially a remote that continues rendering post-logout because it has a stale copy of the auth atom).

`strictVersion: true` must accompany `singleton: true`, otherwise MF silently picks the highest compatible version and logs only a warning — meaning a remote shipped with React 18.3 can coexist with shell's React 18.2 without blocking load, producing subtle runtime bugs.

### 5. `eager: true` is a footgun for auth libraries
Setting `eager: true` on a shared dependency loads it synchronously with the shell entry chunk. For auth/token libs this is often desired (to avoid a flash of unauthenticated UI), but it also means the shared module cannot be lazy-split and increases the shell's critical path. Use `eager` only for:
- React, ReactDOM (required for initial render)
- The shared-ui auth/token bootstrap module
NEVER use `eager` for feature libraries (charts, diagrams, AI cards).

## Security Concerns

1. **CRITICAL — Remote tampering without SRI.** Any remote loaded without SRI is a supply-chain single-point-of-failure. Even if the CDN is hardened, a compromised CI pipeline on one remote can inject arbitrary code into the shell's origin (same-origin from the browser's POV once loaded).
2. **CRITICAL — Allowlist bypass via `Document.prototype.createElement`.** If the monkey-patch is applied on `document.createElement` only (not the prototype), any code running `Document.prototype.createElement.call(document, 'script')` evades the check.
3. **HIGH — Shared state isolation failure.** Without `singleton: true + strictVersion: true`, auth state or token state can be held in a rogue duplicate instance that survives logout.
4. **HIGH — Dynamic `import()` of remote URLs.** If any code path uses `import(/* webpackIgnore: true */ url)` with a user/server-provided URL, it bypasses the allowlist entirely. Ban this pattern in lint.
5. **MEDIUM — SRI hash staleness.** A hash-pinned remote that fails to update on deploy causes full MFE outage. Must be built into the deploy pipeline as a single atomic step (manifest + chunks published together).

## Performance Concerns

1. **Eager shared deps inflate initial bundle** — audit the shell's `shared` config; keep eager set to React/ReactDOM/auth only.
2. **Manifest fetch latency** — the integrity manifest itself must be cached with strict `Cache-Control: no-store` (or a short TTL with versioning) to prevent stale hashes after a remote redeploy.
3. **Runtime plugin overhead is negligible** (microseconds per remote load) — do not trade security for perceived performance here.

## Architectural Implications for frontend-expert reviews

When reviewing the shell or any remote's vite.config.ts / mf config:
1. Verify `remoteIntegrity.ts` is imported as the **first** module in the shell entry (before React, before any other import).
2. Verify the integrity allowlist is loaded from a build-time artifact, NOT hardcoded or fetched at runtime without authenticity checks.
3. Verify the patch targets `Document.prototype.createElement`, not the instance method.
4. Verify the patch rejects BOTH `el.src = url` and `el.setAttribute('src', url)` code paths.
5. Verify every shared dep in the host config matches the corresponding remote's config exactly (name, version, singleton, strictVersion).
6. Flag any `{ singleton: true }` without a matching `{ strictVersion: true }` as HIGH severity.
7. Flag any `{ eager: true }` on a non-bootstrap shared dep as MEDIUM.
8. Verify the deploy pipeline regenerates the integrity manifest atomically with the remote build output (no race window).
9. Flag any direct `import(url)` of a user-influenced URL as CRITICAL.
10. Verify `errorLoadRemote` hook is wired so a failed integrity check surfaces a user-visible error boundary (NOT a silent fallback that masks an attack).

## Domain Rule Additions for frontend-expert

### Module Federation Security (Critical) — additions
- **MUST** declare shared React, ReactDOM, react-router-dom, @tanstack/react-query, zustand with BOTH `singleton: true` AND `strictVersion: true`. Either alone is HIGH.
- **MUST** pin remote entries via SRI (`integrity` attribute on the `<script>`) set from a build-time manifest. A remote loaded without integrity is CRITICAL.
- **MUST** install the `createElement` allowlist patch on `Document.prototype.createElement` — instance-method patching alone is CRITICAL (bypass-trivial).
- **MUST** reject both `.src = url` and `.setAttribute('src', url)` code paths in the patch.
- **MUST** use Module Federation runtime plugin `createScript` hook to attach SRI hashes — do not attempt post-load hash verification in JS (race with execution).
- **MUST NOT** use `{ eager: true }` on any shared dep other than React, ReactDOM, and the auth bootstrap module.
- **MUST NOT** use `import(url)` with any variable derived from user input, server response, or URL params.
- **MUST** atomically publish the integrity manifest alongside the corresponding remote chunks in CI — stale manifest = broken deploy.
- **MUST** wire `errorLoadRemote` to surface a user-visible error boundary with a distinct code for integrity failures (so incidents are detectable in logs).
