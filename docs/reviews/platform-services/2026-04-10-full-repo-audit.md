# Platform Services Review
**Date:** 2026-04-10
**Scope:** `apps/billing-service/**`, `apps/notification-service/**`, `apps/config-service/**`, `apps/event-store-service/**`, `apps/observability-service/**`, `apps/hydroponics-service/**`, `apps/alert-engine/**`, `web/modules/hydroponics-module/**`

**Decision:** BLOCK

**Summary:** CRITICAL 1, HIGH 4, MEDIUM 1, LOW 0

## Findings

1. **CRITICAL-001** Hydroponics nutrient math is still built on native JS `number` arithmetic, and the UI path silently coerces invalid input to `0`. That violates the module rule that nutrient math must use `Decimal` or fixed-point and makes recipe/balance outputs drift under cumulative rounding. Evidence: [`web/modules/hydroponics-module/src/lib/calculator/balance.ts`](/var/aqua-saas/web/modules/hydroponics-module/src/lib/calculator/balance.ts#L7), [`web/modules/hydroponics-module/src/lib/units.ts`](/var/aqua-saas/web/modules/hydroponics-module/src/lib/units.ts#L5), [`web/modules/hydroponics-module/src/components/solution/ParameterRow.tsx`](/var/aqua-saas/web/modules/hydroponics-module/src/components/solution/ParameterRow.tsx#L53), [`web/modules/hydroponics-module/src/components/solution/FertilizerOptionRow.tsx`](/var/aqua-saas/web/modules/hydroponics-module/src/components/solution/FertilizerOptionRow.tsx#L33), [`web/modules/hydroponics-module/src/components/solution/DynamicTankTable.tsx`](/var/aqua-saas/web/modules/hydroponics-module/src/components/solution/DynamicTankTable.tsx#L32). Root cause: the calculation layer was never moved to an exact numeric type, and the input layer collapses parse failures into zero. Remediation: move all recipe, balance, and conversion math to `Decimal` or fixed-point integers and preserve invalid input as validation errors instead of defaulting to zero.

2. **HIGH-002** Billing notifications are effectively stubbed out. `BillingEventHandler` subscribes to `InvoiceOverdue`, `PaymentFailed`, and `SubscriptionCreated`, but every branch just logs and explicitly skips dispatch because the billing contact lookup is "not available yet". That means the notification-service accepts billing events but never sends the customer-facing notifications it is supposed to own. Evidence: [`apps/notification-service/src/notification/event-handlers/billing-event.handler.ts`](/var/aqua-saas/apps/notification-service/src/notification/event-handlers/billing-event.handler.ts#L36) through [`apps/notification-service/src/notification/event-handlers/billing-event.handler.ts`](/var/aqua-saas/apps/notification-service/src/notification/event-handlers/billing-event.handler.ts#L117). Root cause: the handler was shipped before the billing contact resolution path existed, so the event consumer is a no-op. Remediation: wire the handler to a tenant-aware contact source and emit real notifications, or stop subscribing until the full delivery path exists.

3. **HIGH-003** Billing plan mutations do not have the required billing-specific audit trail. `UpdatePlanHandler` mutates `Plan` but has no audit decorator at all, and the other billing mutators rely on generic `@AuditedOperation` instead of a transaction-scoped billing audit entry. Evidence: [`apps/billing-service/src/billing/handlers/update-plan.handler.ts`](/var/aqua-saas/apps/billing-service/src/billing/handlers/update-plan.handler.ts#L13) through [`apps/billing-service/src/billing/handlers/update-plan.handler.ts`](/var/aqua-saas/apps/billing-service/src/billing/handlers/update-plan.handler.ts#L100), plus the generic pattern in [`apps/billing-service/src/billing/handlers/create-subscription.handler.ts`](/var/aqua-saas/apps/billing-service/src/billing/handlers/create-subscription.handler.ts#L10), [`apps/billing-service/src/billing/handlers/record-payment.handler.ts`](/var/aqua-saas/apps/billing-service/src/billing/handlers/record-payment.handler.ts#L10), and [`apps/billing-service/src/app.module.ts`](/var/aqua-saas/apps/billing-service/src/app.module.ts#L141). Root cause: the service has generic audit plumbing, but no billing-specific immutable audit entity/entry path. Remediation: add the mandated billing audit decorator/entry flow to every Invoice/Payment/Subscription/Refund/Plan mutation and write the audit row in the same DB transaction as the business change.

4. **HIGH-004** Event-store projection registration is not tenant-safe. `registeredProjections` is keyed only by `name`, so the last tenant to register a projection overwrites prior registrations with the same projection name. The processing loop then resolves tenant context back out of that single name-keyed map, which can point the loop at the wrong tenant checkpoint and wrong event set. Evidence: [`apps/event-store-service/src/projections/projections.service.ts`](/var/aqua-saas/apps/event-store-service/src/projections/projections.service.ts#L22) through [`apps/event-store-service/src/projections/projections.service.ts`](/var/aqua-saas/apps/event-store-service/src/projections/projections.service.ts#L107), [`apps/event-store-service/src/projections/projections.service.ts`](/var/aqua-saas/apps/event-store-service/src/projections/projections.service.ts#L272) through [`apps/event-store-service/src/projections/projections.service.ts`](/var/aqua-saas/apps/event-store-service/src/projections/projections.service.ts#L329), and [`apps/event-store-service/src/projections/projections.service.ts`](/var/aqua-saas/apps/event-store-service/src/projections/projections.service.ts#L515) through [`apps/event-store-service/src/projections/projections.service.ts`](/var/aqua-saas/apps/event-store-service/src/projections/projections.service.ts#L575). Root cause: tenant identity is stored in the checkpoint table but not in the in-memory registry key. Remediation: key the registry by `(tenantId, projectionName)` and make the processing loop tenant-explicit end to end.

5. **HIGH-005** Notification webhook URL encryption still has an insecure fallback path. If `WEBHOOK_ENCRYPTION_KEY` is missing and `REQUIRE_WEBHOOK_ENCRYPTION_KEY` is not set, the service derives a deterministic dev key and continues startup. That means webhook retry URLs remain decryptable under a misconfigured production deployment. Evidence: [`apps/notification-service/src/notification/services/notification-dispatcher.service.ts`](/var/aqua-saas/apps/notification-service/src/notification/services/notification-dispatcher.service.ts#L40) through [`apps/notification-service/src/notification/services/notification-dispatcher.service.ts`](/var/aqua-saas/apps/notification-service/src/notification/services/notification-dispatcher.service.ts#L49), and [`apps/notification-service/src/notification/services/notification-dispatcher.service.ts`](/var/aqua-saas/apps/notification-service/src/notification/services/notification-dispatcher.service.ts#L167) through [`apps/notification-service/src/notification/services/notification-dispatcher.service.ts`](/var/aqua-saas/apps/notification-service/src/notification/services/notification-dispatcher.service.ts#L199). Root cause: the startup contract allows insecure fallback instead of failing closed. Remediation: make the key mandatory in production and remove the deterministic fallback path entirely.

6. **MEDIUM-006** Tracing is not actually W3C-compliant. `TracingService` defines W3C-length validation regexes, but `startTrace()` and `startSpan()` generate `traceId` and `spanId` with `randomUUID()`, which produces hyphenated UUIDs instead of the required 32-hex / 16-hex identifiers. Evidence: [`apps/observability-service/src/tracing/tracing.service.ts`](/var/aqua-saas/apps/observability-service/src/tracing/tracing.service.ts#L31) through [`apps/observability-service/src/tracing/tracing.service.ts`](/var/aqua-saas/apps/observability-service/src/tracing/tracing.service.ts#L33), [`apps/observability-service/src/tracing/tracing.service.ts`](/var/aqua-saas/apps/observability-service/src/tracing/tracing.service.ts#L67) through [`apps/observability-service/src/tracing/tracing.service.ts`](/var/aqua-saas/apps/observability-service/src/tracing/tracing.service.ts#L121). Root cause: the implementation advertises W3C traceparent semantics but uses the wrong ID generator. Remediation: generate compliant hex trace/span IDs and reject non-compliant IDs at the boundaries.
