# ARIA S1 — what the signed write gate left open (2026-10-02)

Context: kernel step K5 (S1) implemented ADR-0023 on `fix/aria-s1-signed-write-gate` in three
commits (5d46b430e signed MCP writes, 003d28b9a the enrolment chain and its genesis pin, 60d7b72be
read-only trust anchors and the static T2 habitat invariant). The implementer's report named what it
did not build. Each gap below was re-checked against 60d7b72be before it was registered; the ADR is
`docs/recommendations/architectural-arbiter/2026-10-02-adr-0023-signature-namespace-registry.md`.

Owner: claude (implementation), okan (review). Deadline 2026-10-09, the ADR's S1 target.

## ARIA-HIGH-281

ADR-0023's T2 separation has only its static half. The habitat files are pinned, but nothing
measures, as `gharunner`, that the runner cannot read the operator key, has no sudo, is not in the
docker group, holds no personal access token and holds no key the operator allowed-signers file
enrols; and no anchor read refuses an allowed-signers file that enrols a key the kernel registered
for the runner.

Evidence:

- ADR-0023 `:189-190` (key separation: "the S1 probe checks it on every run") and `:277-280` (the T2
  probe runs as an invariant test and as an hourly watchdog probe, K-2′)
- `aria-kernel/aria_kernel/operator_request_signature.py:366` (`_anchor_at` judges the enrolment
  chain and the operators policy; the keys the kernel registered for the runner in `kg_signers` are
  never compared with the enrolled keys)
- `aria-kernel/tests/test_trust_anchor_boundary.py:110` (`RunnerHabitatT2BoundaryTests` reads the
  repository's drop-ins; nothing reads the identity a job actually runs with)
- `scripts/aria/provision_runner.sh:164` (the host units the provisioner installs are the gateway
  and the telemetry export; no probe unit exists)

Rule: The property ADR-0023 builds on, that T2 never signs or approves as the operator, is measured
as T2 every hour, and the kernel refuses an anchor that enrols a key it registered for T2.

## ARIA-MEDIUM-282

The enrolment expiry is judged only when the required check runs. `aria-merge-authority` runs
`test_an_enrolment_this_change_appends_has_not_expired` with the clock of that run, and the merge
authority's pre-merge perimeter, evaluated immediately before ARIA merges, never re-judges the rows
a change appends. A row valid when the check ran can be expired when the merge happens.

Evidence:

- ADR-0023 `:124` and `:133` (journey and enrolment: "at most 168 hours between signing and the
  merge that commits it, checked before merge")
- `aria-kernel/tests/test_operator_signature_namespaces.py:220` (the expiry judged with
  `datetime.now()` of the CI run)
- `.github/workflows/aria-merge-authority.yml:81-93` (the required job runs it at CI time)
- `aria-kernel/aria_kernel/implementation_safety.py:2380` (`readonly_paths_untouched_at_merge`,
  the pre-merge check S1 added, judges changed paths, not the appended rows' expiry)

Rule: An enrolment row is admitted against the clock of the merge decision that lands it, at every
merge decision the kernel owns, and the CI check and that decision share one function.

A human merge is not a decision the kernel owns. GitHub merges a pull request on the verdict of the
check's last run; the merge queue that would run the check at merge time is not available on a
user-owned repository (PROC-LOW-038). A human merge is a T0 or T1 act, and T1 can sign a fresh row
with the same key (ARIA-MEDIUM-273, accepted risk).

## ARIA-MEDIUM-283

An MCP write approval is not single-use. `_write_gate` verifies the signature, the terms and the
expiry, then records the write, but never checks whether the same approval was admitted before, so
one signed operator act admits the identical write again, from any process, until it expires (one
hour by default, 168 at most).

Evidence:

- `aria-kernel/aria_kernel/mcp_server.py:242-259` (`_write_gate`: verify, then append
  `mcp_write_tool_used`; no prior-use check, no lock around the decision)
- `aria-kernel/aria_kernel/mcp_server.py:64` (`mcp_write_subject`: tool, argument digest and terms;
  nothing in the subject is unique to one approval)
- `aria-kernel/aria_kernel/operator_approval.py:288` (`_consume`: the GitHub-approval path spends
  its act under the governance ledger's lock; the MCP path has no equivalent)

Rule: One signed operator act authorizes one write. A second use is refused, including from another
process, and the record of the use lives on a declared, hash-chained ledger the integrity verifier
covers.
