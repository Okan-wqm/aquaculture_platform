## Key Findings

### Article 15 — Right of Access
- Data subject has the right to obtain confirmation of processing + a COPY of personal data.
- Required supplementary info: purposes, categories of data, recipients, retention duration, rights (rectification/erasure/restriction), origin, automated decision-making/profiling.
- Response MUST be in a commonly used electronic form (JSON, CSV).
- Response MUST be within 1 month (extendable to 3 months for complex requests).

### Article 16 — Rectification
- Subject can correct inaccurate data; controller must update without undue delay.
- Must propagate to downstream recipients/processors.

### Article 17 — Right to Erasure
- Erasure required when: data no longer necessary, consent withdrawn, subject objects (no overriding legitimate ground), unlawful processing, legal obligation, child consent.
- Exceptions: freedom of expression, legal obligation to retain, public interest, legal claims.
- If data was made public, controller MUST "take reasonable steps, including technical measures, to inform other controllers" — cascade deletion across recipients.
- Response within 1 month.

### Article 18 — Restriction of Processing
- Subject can restrict (but not delete) processing pending verification (accuracy dispute, objection review, legal claims).
- Implementation: soft-delete or "restricted" flag; data remains in DB but cannot be processed (read-only, excluded from analytics, excluded from email campaigns).

### Article 20 — Data Portability
- Subject can receive their data in a **structured, commonly used, machine-readable format** (JSON preferred, CSV acceptable).
- Subject can transmit data to another controller "without hindrance" — controller must NOT block direct transmission.
- Scope: only data provided by the subject OR generated by the subject's activity (NOT derived data like risk scores).

### Anonymization vs pseudonymization
- **Anonymization:** irreversible; data can no longer be linked to a subject. After anonymization, GDPR no longer applies.
- **Pseudonymization:** reversible with additional information kept separately (e.g., hash mapping). Still GDPR-scoped.
- Anonymization must use **cryptographically random replacement values** (e.g., `crypto.randomUUID()` for IDs, `randomBytes()` for strings). Counter-based or predictable values defeat anonymization.

### PII redaction in logs (OWASP)
- OWASP: data that should not be logged directly includes sensitive PII (health/gov identifiers), passwords, card data, crypto keys.
- OWASP: "Non-sensitive PII (names, phones, emails) should consider de-identification: deletion, scrambling, pseudonymization."
- Implement `SENSITIVE_FIELDS` list + `isSensitiveField()` helper. Every logger wrapper must traverse objects and redact matching keys.
- Common field list: `password`, `passwordHash`, `refreshToken`, `token`, `secret`, `apiKey`, `creditCard`, `ssn`, `mfaSecret`, `recoveryCodes`, `email`, `phone`, `firstName`, `lastName` (email/name depending on context).

### Export link lifecycle
- Exports are large files (full user data, often 10s of MB). Stored in object storage (S3/MinIO) with signed URL.
- **Signed URL MUST expire** — OWASP recommendation: short lifetime (24 hours typical, 7 days max).
- Signed URL MUST be single-use (track `consumed` flag in DB) or short enough that reuse is low-risk.
- Email containing the link must use TLS; link itself must NOT be indexable/searchable.

### Cascade deletion across tenants
- Deleting a user must cascade across all related tables in the tenant schema.
- Cross-tenant: messages, audit logs containing the user's ID, announcements, session history.
- Audit logs should retain the ACTION but anonymize the actor (replace with `DELETED_USER_<uuid>`) to maintain forensic integrity without breaching GDPR.
- Foreign keys should use `ON DELETE SET NULL` or `ON DELETE CASCADE` based on whether the record's historical existence is necessary.

### Erasure verification (auditable)
- After erasure, generate a cryptographic proof-of-erasure record: `{userId_hash, erasedAt, operatorId, method}`.
- Proof-of-erasure is retained even after user erasure (it contains the HASH of the userId, not the userId itself).
- Useful for compliance audits: "yes, user X was erased on date Y."

### GdprService interface (reference shape)
- `exportUserData(userId)` — Art. 15 + Art. 20 combined. Returns JSON + generates signed URL.
- `rectifyUserData(userId, changes)` — Art. 16. Applies changes + propagates.
- `eraseUserData(userId, reason)` — Art. 17. Cascades + anonymizes + emits proof-of-erasure.
- `restrictUserProcessing(userId, scope)` — Art. 18. Soft-flags records.
- `revokeConsent(userId, purpose)` — stop processing under that legal basis.

## Security Concerns
- **CRITICAL:** Anonymization using predictable values (e.g., `user_${id}`) = trivial re-identification.
- **CRITICAL:** Missing PII redaction in logs = email/name/phone in log files = GDPR breach (Art. 32).
- **CRITICAL:** Export links without expiry = long-lived data leak surface.
- **CRITICAL:** Erasure not cascading across all schemas/services = incomplete erasure = GDPR non-compliance.
- **HIGH:** Export link transmitted over non-TLS email = interception.
- **HIGH:** No proof-of-erasure = cannot demonstrate compliance to regulators.
- **HIGH:** JWTs carrying PII (email, firstName) = every log line with token dump = PII leak.
- **MEDIUM:** Missing Art. 18 (restriction) implementation = cannot satisfy subject requests.

## Performance Concerns
- Full user data export can be slow (dozens of table scans). Run as async job with progress tracking.
- Erasure must be transactional across tables. Large users = long-running transaction. Prefer chunked deletion with "erasure in progress" flag.
- PII redaction in logger adds ~0.2ms per log line (object traversal). Acceptable.

## Architectural Implications
- GdprService coordinates with every bounded context (farm, sensor, messaging, etc.) via explicit interface or event — each context must expose its own `eraseUserData(userId)` handler.
- Export links stored in S3 with bucket-level lifecycle policy (auto-delete after N days).
- `SENSITIVE_FIELDS` is a shared const in `@platform/logging` used by all services.
- JWT payload audit: strip PII (Historic finding H-08). Services needing profile fetch via NATS/REST.

## Domain Rule Additions
- **CRITICAL:** Anonymization MUST use cryptographically random replacement values (`crypto.randomBytes`, `crypto.randomUUID`). Predictable values are CRITICAL.
- **CRITICAL:** Export signed URLs MUST expire within 7 days maximum. Default 24 hours for sensitive exports.
- **CRITICAL:** PII redaction via `SENSITIVE_FIELDS` + `isSensitiveField()` MUST run on every logger call. Logging PII is CRITICAL.
- **CRITICAL:** JWTs MUST NOT carry PII (email, firstName, lastName). Services fetch profile via NATS/REST.
- **CRITICAL:** Erasure MUST cascade across all bounded contexts via event fan-out or explicit interface. Incomplete erasure is CRITICAL.
- GdprService MUST implement all of Art. 15, 16, 17, 18, 20. Missing any is a compliance violation.
- Erasure MUST emit a proof-of-erasure audit record with hashed userId.
- Audit log retention after user erasure: anonymize actor (`DELETED_USER_<uuid>`) while preserving action.
- Restriction (Art. 18) MUST soft-flag records; processing pipelines MUST honor the flag.
- Response to subject requests MUST be within 1 month (Art. 12).
